# AGENTS.md

## Что это

`my-first-agent` — stateful CLI-агент для DeepSeek через OpenAI-совместимый SDK. Линтер и форматтер — Biome, тесты — Vitest, CI — GitHub Actions.

## Учебный подход

Цель курса — научиться создавать собственных агентов. Приоритет — простая, понятная реализация, которая раскрывает изучаемое поведение и выполняет задание с учётом уточнений ментора.

- Для нового задания сначала определить учебную цель и минимально достаточный результат. Дополнительные улучшения отделять от обязательной части.
- Развивать существующего агента небольшими изменениями. Новые зависимости, абстракции, универсальные механизмы и инфраструктуру добавлять только при конкретной необходимости текущего задания.
- Если требования допускают приближение, использовать простые эвристики, искусственные ограничения и тестовые данные. Явно обозначать оценки и симуляции, отличая их от измерений и поведения реального API.
- Сравнения сценариев использовать для проверки и понимания поведения. Отдельные программы экспериментов, отчёты и демонстрационные системы создавать, только если они нужны по заданию.
- Если достаточно показать ошибку и её причину, автоматическое восстановление не входит в минимальную реализацию. Простота не отменяет корректность состояния, существующие инварианты и содержательные тесты.
- В объяснениях связывать изменение с тем, чему оно учит при создании агента. Подтверждённые ответы ментора использовать как ориентир по масштабу; точные требования нового задания имеют приоритет, неполученные ответы не считать согласованными.

## Сценарии для видео

- Приоритет — быстрая ручная демонстрация с простым результатом. Ориентир — 4–6 коротких пользовательских реплик на сценарий, если задание не требует большего объёма; использовать минимум вымышленных фактов.
- Ускорять проявление поведения небольшими параметрами запуска. Для демонстрации окна контекста предпочитать `AGENT_KEEP_LAST_MESSAGES=2`, при необходимости 4. N считает сообщения: вопрос и ответ занимают два. Заранее проверять, какие ходы останутся к контрольному вопросу.
- При сравнении стратегий использовать одинаковые реплики, модель и чистую историю. Для проверки памяти достаточно исходных условий, исправления, отмены и короткого итогового вопроса. Просить промежуточный ответ «Принято»: это сокращает видео и уменьшает перенос ранних фактов в новые ответы.
- Давать готовые команды запуска, сброса и реплики отдельными блоками для копирования. Рядом указывать краткий ожидаемый результат и что показать на экране. Учитывать, что сброс очищает прежнюю историю выбранного режима, но не рабочую и долговременную память.
- Специфические возможности показывать коротким дополнением. Для Branching достаточно одного checkpoint, двух вариантов и возврата в первый — обычно трёх дополнительных запросов к модели.
- Ожидаемое поведение отличать от фактического результата, не обещать точные ответы модели. Сравнивать расход всей основной части, включая служебные вызовы Facts; дополнительные ветки считать отдельно. Длинный автоматический эксперимент не делать обязательным для короткого видео.

Примеры: [короткий сценарий слоёв памяти](docs/memory-video-prompts.md), [профили агента](docs/profile-video-prompts.md), [задача как конечный автомат](docs/task-video-prompts.md), [инварианты ответа](docs/invariants-video-prompts.md).

## Архитектура

`src/index.ts` собирает окружение, SDK, `JsonProfilesRepository` и `AgentSession` с фабрикой `Agent` и `SUPPORT_INVARIANTS`; репозитории истории, памяти и задачи даёт `jsonAgentRepositories(root, contextStrategy)`. Каталог данных — всегда `process.cwd()`, общий для всех профилей агента. Внутри обычный режим (contextStrategy=null) и Compression используют `.agent-history.json`, три новых режима — `.agent-history.<contextStrategy>.json`. Интерактивный и однократный CLI используют один файл выбранного режима. Старый формат `{ summary, messages }` и JSON-массив поддерживаются для обычного режима и compression, при чтении файл не переписывается. Рабочая и долговременная память — `.agent-memory.working.json` и `.agent-memory.long-term.json` того же каталога, общие для всех режимов, веток и профилей. Задача с перепиской — `.agent-task.json` того же каталога, тоже общая для всех режимов. `src/cli.ts` работает только с `SessionPort` (AgentPort и операции профилей) и не знает формат API или хранилище: разбирает команды, ведёт цикл чтения и опрос профиля. Оформление — `src/cli-view.ts`: смысловые стили, блоки, токены, состояние задачи, справка и пары «ключ: значение» (см. «Вывод CLI»).

`src/agent.ts` владеет конфигурацией, тремя слоями памяти, задачей и расходом токенов. Профиль не хранит: необязательный синхронный `profileProvider` вызывается один раз в начале `respond()`, копия используется всеми вызовами хода. История, рабочая и долговременная память, затем задача загружаются по одному разу в конструкторе после проверки конфигурации; kind истории должен совпадать с contextStrategy, для null используется тот же формат kind=compression. Если задача есть и не на паузе, `respond()` выполняет task-ход (см. «Задача»). Иначе готовит полный диалог, окно или активную ветку, обновляет кандидат summary или facts при необходимости, выполняет meta и финальный запрос, учитывает usage, проверяет ответ и инварианты (при нарушении — одна повторная генерация), сохраняет историю, затем заменяет её в агенте. Рабочую и долговременную память `respond()` не меняет. `src/tokens.ts` оценивает текст и стек по длине content; бюджет проверяется перед каждым вызовом.

`src/history.ts` содержит HistoryMessage, ContextStrategy, различаемое объединение HistoryState и синхронный контракт HistoryRepository: load() возвращает состояние или null при отсутствии файла, save() сохраняет состояние. Форматы в памяти: compression — `{ kind, summary, messages }`, sliding — `{ kind, messages }`, facts — `{ kind, messages, facts }`, branching — `{ kind, activeBranch, branches, checkpoint }`. `src/json-history-repository.ts` проверяет Zod-схему, порядок пар во всех историях, наличие main и активной ветки; сохраняет через `src/json-file.ts`: временный файл рядом с основным и renameSync. Compression сохраняется на диск без kind, в прежнем формате `{ summary, messages }`. Без репозитория история живёт только в экземпляре агента.

`src/memory.ts` содержит MemoryLayer (short/working/long), MemoryEntries, MemorySnapshot, синхронный контракт MemoryRepository, правило ключа, заголовки блоков и инструкцию интерпретации памяти. `src/json-memory-repository.ts` — одна реализация для обоих словарей: Zod-схема при load и save, ошибки со слоем, путём и причиной. Ключ `__proto__` отклоняется отдельно: Zod record молча отбрасывает его. Запись идёт через тот же `src/json-file.ts`; `replaceFile` создаёт отсутствующий каталог. Без репозитория словарь живёт только в экземпляре агента.

`src/task.ts` содержит TaskState, TaskContext, TaskSnapshot, контракт TaskRepository, таблицу TASK_TRANSITIONS, разрешённые действия этапов, Zod-схему ответа модели, инструкции и чистые функции: создание, утверждение плана, применение действия, производный статус, блок данных запроса и проверку согласованности снимка. `src/json-task-repository.ts` проверяет схему и согласованность при load и save; `null` в файле — задачи нет; запись через `src/json-file.ts`.

`src/profile.ts` содержит AgentProfile (style/constraints/context), ProfilesState, контракт ProfilesRepository, правило profileId, заголовок блока и инструкции профиля. `src/json-profiles-repository.ts` проверяет `.agent-profiles.json` Zod-схемой при load и save: неизвестные поля, неверные типы, пустые значения, недопустимые идентификаторы (включая `__proto__`) и activeProfileId без записи отклоняются; прежний каталог с `activeUserId` отклоняется при load отдельным сообщением без изменения файла; ошибки содержат путь и причину без профилей. `src/session.ts` — `AgentSession`: владеет каталогом профилей и единственным `Agent`, созданным при запуске; его `profileProvider` читает текущий `activeProfileId` сессии. Делегирует AgentPort и блокирует выбор и запись профилей на всё время `respond()`.

`src/invariants.ts` содержит абстрактный `Invariant` (`id`, `description`, `check(response)`), InvariantInfo, результат проверки, чистую `validateInvariants`, заголовок блока, инструкции для модели, meta и повтора. `src/support-invariants.ts` — четыре правила службы поддержки на регулярных выражениях и замороженный `SUPPORT_INVARIANTS` (см. «Инварианты ответа»).

Настройки одного агента находятся в AgentConfig. `strategy` выбирает prompting (direct/steps/meta/experts), `contextStrategy` — управление контекстом.

## Инварианты

- Во всех историях, checkpoint и переписке задачи только завершённые пары user/assistant. В обычном чате непустой финальный ответ с validation.ok === false или finishReason === length также сохраняется, если прошёл инварианты; ответ задачи — только при finish_reason stop, валидной схеме, формате answer, допустимом действии и соблюдённых инвариантах.
- При load/save копируется всё вложенное состояние: сообщения, facts, ветки и checkpoint не разделяют изменяемые ссылки с репозиторием.
- Любая запись выполняется как кандидат → save → замена состояния агента. Ошибка сохранения не меняет состояние; usage полученных API-ответов остаётся. Автоматического повторного хода нет; единственная повторная генерация — при нарушении инвариантов ответа.
- reset() очищает весь выбранный режим, включая facts, все ветки и checkpoint. Branching возвращается к пустой main. Только успешная запись очищает статистику; конфигурация, другие файлы режимов, рабочая и долговременная память сохраняются. clearMemory("short") — то же, что reset().
- Только ENOENT означает отсутствие истории или словаря памяти. Другие ошибки загрузки останавливают запуск, не меняя файл; ошибки содержат причину и путь (для памяти — и слой), без диалога, записей памяти и стека.
- Конфигурация, ключ, оценки и usage не сохраняются. kind обозначает формат состояния. После перезапуска восстанавливаются данные и активная ветка, статистика начинается с нуля.
- Системный промпт собирается заново для каждого вызова, служебные summary-, facts- и meta-запросы в диалог не записываются.
- tokenEstimate измеряет вопрос после trim() и стек финального вызова, чей ответ возвращён, до генерации. usage.summaryCall, factsCall, finalCall, turn и session — независимые снимки; reasoning входит в генерацию.
- maxInputTokens: null отключает бюджет. Превышение блокирует вызов до API, не меняет историю и освобождает busy; равенство разрешено. Уже потраченный usage summary, facts, meta и отклонённого инвариантами ответа сохраняется при блокировке следующего вызова.
- Пустой ответ учитывается в usage; ошибка транспорта без ответа usage не меняет. Отсутствующий provider usage даёт нулевой fallback, а не измеренный нулевой расход.
- busy охватывает весь respond(), включая save; параллельные ходы, reset, изменения веток, памяти и задачи запрещены. Чтение статуса, списка веток, снимка памяти и задачи не меняет состояние. Сессия так же запрещает выбор и запись профилей; чтение профилей разрешено.
- Рабочая и долговременная память меняются только явными setMemory, deleteMemory и clearMemory. respond(), summary, facts, checkpoint и ветки их не меняют; прежние facts в словари не переносятся. Одна операция пишет один файл; deleteMemory отсутствующего ключа возвращает false без записи.
- Словарь — плоский Record<string, string>. Ключ 1–64 символа (буквы, цифры, дефис, подчёркивание; первый — буква или цифра), регистр важен; значение непустое, при записи крайние пробелы обрезаются. Наличие ключа проверяется Object.hasOwn, изменение создаёт новый объект. getMemory() возвращает глубокую копию; загруженные и переданные в save словари не разделяют ссылок с агентом.
- Непустой профиль идёт отдельным user-блоком сразу после system, за ним блок инвариантов, если они переданы, затем непустые словари: long, затем working, затем summary или facts, сообщения и вопрос. Инструкция интерпретации добавляется в system только при непустой памяти; при пустых словарях запросы и оценки прежние. Meta и финальный запрос используют один снимок; служебные summary и facts словари не получают. Блоки входят в оценку и бюджет; подсказка при переполнении meta или финального запроса упоминает /memory только при непустой памяти.
- API-ключ не входит в AgentConfig и не возвращается в AgentResult.
- Каталог профилей меняется как проверка → кандидат → save → замена состояния; чтение файл не переписывает. Смена профиля: проверка profileId и записи → кандидат каталога → save activeProfileId → замена состояния сессии. Агент не пересоздаётся, история и память не перечитываются, задача и usage не сбрасываются. Ошибка оставляет прежние профиль и каталог. Повторный выбор активного профиля ничего не пишет.
- Выбор, создание и правка профиля сохраняют агента, диалог, память, задачу и usage; новую статистику начинают перезапуск и очистка short. Профиль не попадает в историю, summary, facts и служебные запросы; respond не меняет профиль.

## Слои памяти

`short` — HistoryState выбранной стратегии: сообщения, summary, facts, ветки, checkpoint. `working` — условия текущей задачи, `long` — сведения, предпочтения и знания. Все три слоя общие для всех профилей агента; роль, ограничения и стиль хранятся в профиле. Оба словаря пишутся только командами пользователя, автоматического извлечения нет; наставник подтвердил, что явных команд достаточно. Это не contextStrategy и не переключатель: непустые словари добавляются к любому режиму.

Интерактивный CLI: `/memory`, `/memory show short|working|long`, `/memory set working|long ключ значение`, `/memory delete working|long ключ`, `/memory clear short|working|long`. Команды и слои регистронезависимы, регистр ключей и значений сохраняется. Значение set — остаток строки после ключа, без обработки кавычек. Команды не вызывают LLM, не попадают в диалог и не меняют usage; статистику сбрасывает только очистка short. Однократный запуск с аргументом на `/` завершается кодом 1 без вызова модели. Новый разговор — две самостоятельные команды: `/reset` и `/memory clear working`; задачу автомата они не меняют.

Ограничения: удаление записи не удаляет её упоминаний из истории, summary и facts; ответ ассистента может повторить запись в short. `/reset` очищает историю только выбранного режима, другой режим может восстановить прежний разговор. Изменение working видно во всех ветках, режимах и профилях. Одна текущая задача на рабочий каталог, один пишущий процесс на рабочий каталог, без межфайловых транзакций.

## Задача

Задача — конечный автомат `planning → execution → validation → done` для одной текстовой работы. Это не слой памяти и не contextStrategy: пока задача есть и не на паузе, `respond()` использует её вместо обычного диалога, в том числе в done — для обсуждения результата. Execution — подготовка результата в ответах модели, validation — проверка текста моделью по требованиям задачи; файлы, команды и отправка сообщений не входят.

TaskContext: `task` (описание после trim), `state`, `paused`, `plan`, `results[i]` — полный результат `plan[i]`, `waitingFor` — открытый вопрос, `review` — последняя проверка. TaskSnapshot — контекст и собственная переписка. Число шагов, текущий шаг (`results.length + 1`) и его название не хранятся, а вычисляются. Статус для CLI и запроса: этап, пауза, текущая работа, шаг, ожидаемое действие (пауза → вопрос → утверждение плана → уточнение или план → шаг → проверка → нет действий).

Переходы: planning → execution (только `/task approve`), execution → validation (последний `complete_step`), execution → planning (`replan`), validation → execution (`validation_fail`), validation → done (`validation_pass`); из done переходов нет. Действия модели: `reply` — любой этап, очищает вопрос; `ask` — кроме done, в planning сбрасывает черновик плана; `propose_plan` — planning, этап не меняет; `complete_step` — execution, один результат за ход, после последнего — validation без немедленной проверки; `replan` — очищает план, результаты, вопрос и проверку, новый план снова утверждается; `validation_pass` — `{ passed: true }`, done; `validation_fail` — `restartAt` от 1 до числа шагов, результаты с этого шага удаляются, `{ passed: false }` сохраняется до следующей проверки.

Task-ход: снимок контекста → meta (если выбрана, с `TASK_META_INSTRUCTION`) и финальный вызов в JSON mode → finish_reason stop → JSON → строгая схема → формат `answer` существующим валидатором → применение действия → проверка согласованности → инварианты по `answer` и `steps` → пара user/`answer` → одна запись TaskSnapshot → замена состояния. Любая ошибка до записи оставляет прежний снимок, пара не сохраняется; повторный вызов — только один, при нарушении инвариантов корректным по протоколу ответом, от исходного снимка. Стек: system (+ инструкции профиля, инвариантов и памяти, стратегия или ответ meta, `TASK_INSTRUCTION`, при инвариантах `TASK_INVARIANTS_INSTRUCTION`, требования `format` и `maxWords` к `answer`) → профиль, инварианты, long, working → блок данных задачи со статусом и `allowedActions` → вся переписка задачи → реплика. Stop marker не передаётся. summaryCall и factsCall равны null. Compression, окно, facts и ветки к задаче не применяются; автоматического сжатия нет, подсказка бюджета предлагает `/task clear` или `/task pause` и не обещает очистку через `/reset`.

Команды `/task`, `/task start описание`, `/task approve`, `/task pause`, `/task resume`, `/task clear` — только интерактивные, регистронезависимые, без LLM и usage; описание — остаток строки с исходным регистром и пробелами. `start` отклоняет пустое описание и замену незавершённой, в том числе приостановленной, задачи; завершённую заменяет. `approve` — только planning с планом, без вопроса и паузы. Повторные `pause`/`resume` и `clear` без задачи ничего не пишут и возвращают false; `approve`, `pause`, `resume` без задачи — ошибка. Блок «Состояние задачи» показывается при запуске, после команд и task-ходов; черновик плана planning без открытого вопроса выводится в нём из `context.plan` после task-хода, при запуске и после `/task resume`, `waitingFor` — при запуске и после `/task resume`; полный `/task` показывает план и вопрос отдельными блоками по одному разу; приглашение — `profileId [задача] > ` или `profileId [чат, задача на паузе] > `, без задачи прежнее. Смена профиля задачу не меняет: план не утверждается, этап, результаты, вопрос и пауза сохраняются.

Инварианты снимка при load, save и кандидате хода: непустые строки, завершённые пары, результатов не больше шагов; planning — без результатов и review; execution — непустой план и незавершённый шаг; validation и done — результат каждого шага; done — положительный review без вопроса; положительный review только в done. `/reset`, `/memory clear short`, ветки и смена contextStrategy задачу не меняют; `/task clear` сохраняет `null`, не трогая историю, профили, память и usage. Ошибки схемы ответа и файла называют путь и причину без значений и названий неизвестных полей. Архива задач, отмены запроса в полёте и миграции прежних файлов нет.

## Профили агента

Профиль агента — `{ style?, constraints?, context? }`: context — роль и предметная область, constraints — рабочие ограничения, style — тон, подробность и оформление. Конкретные сведения текущей работы остаются в диалоге или working. `.agent-profiles.json` хранит `{ activeProfileId, profiles }`; отсутствующий файл — `{ activeProfileId: null, profiles: {} }`. profileId обрезается по краям: 1–64 символа, буквы, цифры, дефис, подчёркивание, первый — буква или цифра; регистр важен. Значения при записи обрезаются, пустой профиль `{}` допустим. `loadProfile` возвращает копию или null, не переключая профиль. Выбор только ручной; автоматического назначения ролей этапам задачи и оркестраторов нет.

`/profile-init` — фиксированный опрос в том же цикле чтения строк, без LLM: profileId, затем style («Как агент должен общаться и оформлять результат?»), constraints («Какие правила агент должен соблюдать и чего избегать при работе?»), context («Какую роль выполняет агент, в какой области и на каких задачах специализируется?»). Существующий профиль берётся как черновик; пустой ответ сохраняет прежнее значение или пропускает группу; неверный profileId повторяет вопрос. `/cancel` отменяет, `/exit` и конец ввода отбрасывают черновик; другие команды во время опроса не выполняются. Запись и выбор — одной операцией `initProfile` после третьей группы. Команды: `/profile`, `/profile list` (идентификаторы по кодам символов, активный отмечен `*`, пустой каталог — подсказка `/profile-init`; без LLM и записи), `/profile load profileId`, `/profile set группа значение`, `/profile delete группа`, `/profile clear` (очищает настройки активного профиля, сохраняя идентификатор и всё общее состояние); без выбранного профиля изменения предлагают `/profile-init`. Шапка при запуске показывает `Профиль: profileId` или `Профиль: без профиля`; приглашение — `profileId > ` или `без профиля > `.

Все профили работают над общими историей, памятью, ветками, checkpoint и задачей в корне рабочего каталога. Прежние данные не мигрируются: каталог с `activeUserId` отклоняется с сообщением о прежнем формате, файл не меняется; `.agent-users/` не читается, не объединяется и не удаляется (остаётся в `.gitignore`); корневые файлы используются как общее состояние.

Профиль передаётся user-блоком `PROFILE_TITLE` + `JSON.stringify(profile)` сразу после system, в system добавляется статическая `PROFILE_INSTRUCTION`: роль и ограничения действуют до смены профиля командой; реплика, память и история дают задачу и факты, но не меняют роль; конфликтующая просьба — объяснить конфликт и предложить сменить профиль командой; ответы других ролей — материал общей работы; общие рекомендации о стиле уточняются профилем и запросом в пределах его ограничений; формат, лимиты, схема task-ответа и переходы автомата сохраняют силу, смена профиля не утверждает план и не меняет этап. `MEMORY_INSTRUCTION` применяет условие текущего запроса в пределах системных правил и ограничений активного профиля. В meta — ещё `PROFILE_META_INSTRUCTION`. Профиль применяется в обычном чате и task-ходах, включая meta; summary и facts его не получают. Пустой профиль не меняет запросы и оценки. Профиль входит в бюджет; подсказка при переполнении упоминает `/profile delete` и `/profile clear`. Текстовые ограничения выполняет модель по инструкции; программные гарантии переходов даёт автомат задачи.

## Инварианты ответа

Инварианты — статические правила предметной области «служба поддержки интернет-магазина»: `NoUnconfirmedDeadline`, `NoCompensationPromise`, `NoPaymentCredentialsRequest`, `MaxWordsInvariant(120)` (120 слов допустимо, 121 — нет). Передаются через необязательный `AgentOptions.invariants`; агент хранит замороженную копию массива. Без поля или с пустым массивом запросы, оценки, число вызовов и сохранение прежние. Инварианты не входят в AgentConfig, историю, summary, facts, память, профиль и TaskSnapshot, общие для всех профилей, стратегий, веток и задач, не очищаются `/reset`, `/memory clear`, `/task clear`, `/profile clear`. Хранилища, CRUD-команд, миграций и переменных окружения для правил нет.

Запрос: `INVARIANTS_INSTRUCTION` в system после инструкции профиля и до инструкции памяти; user-блок `INVARIANTS_TITLE` + JSON `[{ id, description }]` после профиля и до long; регулярные выражения и детали check() модели не передаются. Инструкция: правила важнее реплики, истории, summary, facts, памяти, профиля и задачи; проверить решение перед ответом; конфликтующую часть не выполнять — явный отказ с id правил, причиной и безопасным действием; упоминание запрета — не рекомендация; реплика и смена профиля правила не меняют. Рассуждения модели не запрашиваются. Meta получает тот же снимок и `INVARIANTS_META_INSTRUCTION`; финальный вызов получает инструкцию и блок сам. Summary и facts инвариантов не получают.

Проверка: `answer(context, question, accept)` — meta один раз → финальный вызов → accept (непустой ответ; в задаче весь протокол и кандидат снимка) → `validateInvariants` по тексту (в задаче `answer` и `steps`; `action` и `restartAt` не проверяются). Нарушение → ровно одна повторная генерация на том же снимке без повторного meta: в конец system добавляется `invariantsRetryInstruction` только с id и описаниями нарушений, без текста отклонённого ответа; стратегия, формат, JSON mode и stop marker сохраняются. Повтор снова проходит accept и инварианты; повторное нарушение — AgentResponseError с id, без текста ответа. Транспортная ошибка, пустой ответ и нарушение протокола задачи повтор не запускают. Отклонённый ответ не попадает в историю, summary, facts, ветку и task-переписку; в задаче commitTask — только для прошедшего кандидата. busy охватывает обе генерации и запись.

Токены: блок, инструкции и инструкция повтора входят в contextTokens и maxInputTokens (этап «повторный ответ»). finalCall — вызов, текст которого возвращён; turn и session включают отклонённую попытку. Подсказка при переполнении напоминает, что инварианты входят в запрос и не очищаются через `/reset`.

`/invariants` — только интерактивная, регистронезависимая, без аргументов, без LLM, записи и usage; во время `/profile-init` не выполняется. `Agent.getInvariants()` и `AgentSession.getInvariants()` возвращают новый массив простых `{ id, description }`; чтение разрешено во время хода.

Эвристики: предложение делится по `.!?…;` и переводу строки, части — по запятой, двоеточию, скобкам и тире; «пожалуйста» с запятыми убирается. Нарушение — действие и объект в одной части без отрицания перед действием, без отрицаемой модальности («не могу», «нельзя») и вне придаточного «что …» после отрицаемой главной части до «но». Для компенсации объект не дальше двух слов от глагола и без предлогов между ними. Перефразировки не распознаются; примеры обоих направлений — `tests/invariants.test.ts`.

## Стратегии контекста

`contextStrategy` / `AGENT_CONTEXT_STRATEGY`: null (default, полная история без обработки), compression, sliding, facts, branching. Пустое значение, пробелы или отсутствие переменной дают null; неверное непустое значение — ошибка. Выбор при запуске; обычный режим и compression продолжают один диалог в `.agent-history.json`, три новых режима используют отдельные истории. `historyCompressionEnabled` удалён, `AGENT_HISTORY_COMPRESSION` больше не читается. `historyKeepLastMessages` / `AGENT_KEEP_LAST_MESSAGES` по умолчанию 10; N — положительное чётное безопасное целое, число сообщений, не пар; в обычном режиме и Branching не ограничивает историю.

Без стратегии отправляется и сохраняется вся история, включая существующее summary, без новых сжатий, окна, facts или веток. Контекст растёт до бюджета или лимита API. Выбор compression включает периодическое сжатие без дополнительного флага. При `messages.length >= N + 10` перед вопросом префикс кроме последних N сообщений заменяется summary. При N=10 сжатие перед вопросами 11, 16, 21; после ответа хвост N+2, между сжатиями растёт. Запрос получает только прежнее summary и префикс, max_tokens=512, thinking disabled, без meta и политики ответа. Пустое или усечённое summary — ошибка после учёта usage. Стек: system → summary как данные в user → хвост → вопрос. Meta и финальный вызов используют общий кандидат; summary и новая пара фиксируются вместе. Возврат к null запрещает новые summary, сохраняя существующее и всю дальнейшую историю. В трёх новых режимах сжатие не выполняется. reset() в обычном режиме и Compression сохраняет прежнее `{ summary: null, messages: [] }` на диск.

Sliding отправляет system → последние N завершённых сообщений → новый вопрос. После ответа сохраняет последние N сообщений с учётом новой пары; префикс удаляется. Более длинная загруженная история ограничивается до запроса и обрезается при следующем успешном save.

Facts перед каждым ответом обновляет весь Record<string, string> отдельным запросом той же модели: прежние facts + последние N сообщений + вопрос. `src/facts.ts` содержит инструкцию и схему непустых строк. Обновление использует JSON mode, max_tokens=512, thinking disabled, без meta и политики финального ответа. Пустой, усечённый, невалидный JSON или неверная структура — ошибка после учёта usage, без автоматического восстановления. Исправления и отмены извлекает модель; Zod проверяет структуру, а не достоверность.

Обновлённые facts допускают в ключах только латинские буквы, цифры, `_` и `-`, первый символ — латинская буква. Инструкция просит английские названия в snake_case, например `conversation_code`; язык значений сохраняется. Старые ключи на других языках загружаются без изменения файла и передаются модели для переименования при следующем обновлении. Ответ модели с недопустимым ключом отклоняется без сохранения хода.

Инструкция facts содержит пример плоского словаря: числа, даты и логические факты записываются строками, вложенные объекты и обёртка facts запрещены. Запрашиваемые неизвестные сведения пропускаются без создания пустых значений; просьба обозначить неизвестное «не знаю» относится к финальному ответу. Пример вопроса при пустых facts и истории возвращает `{}`; существующие факты сохраняются по общим правилам. JSON mode не гарантирует схему. Ошибка валидации сообщает причину и полученный тип без содержимого фактов.

Ответ в Facts получает system → facts как данные в user-сообщении → последние N сообщений → вопрос. Meta и финальный вызов используют один обновлённый кандидат. Facts фиксируются только вместе с завершённой парой. factsCall равен null в других режимах; turn включает summary + facts + meta + финальный вызов; summaryCall равен null без сжатия.

Branching хранит полную историю каждой ветки и отправляет только активную, без окна и facts. `/checkpoint` заменяет единственный снимок копией активного диалога. `/branch имя` создаёт и выбирает независимую копию checkpoint, независимо от текущей ветки. `/switch имя` сохраняет выбор; `/branches` показывает имена, активную ветку и число сообщений. Имена уникальны: 1–64 символа, буквы, цифры, дефис и подчёркивание, первый символ — буква или цифра. Команды веток доступны только в интерактивном Branching, LLM не вызывают и токенов не расходуют.

Один файл рассчитан на один пишущий процесс; атомарная замена не разрешает конфликты двух CLI. Facts могут терять или искажать детали; ветки и словарь не имеют автоматического ограничения размера. Нет общего архива для Sliding/Facts, восстановления вытесненных сообщений, объединения веток, дерева checkpoint, поиска, SQLite, блокировок или сохранения usage. Ограничения демонстрируются явно, без автоматического восстановления.

## Вывод CLI

Интерактивный запуск: шапка `── my-first-agent ──`, профиль, стратегия и ветка, строка `Команды: /help · /task · /memory · /profile · /invariants`, блок задачи, приглашение. Полная справка — только `/help`: группы Диалог, Задача, Память, Профиль, Инварианты, Ветки. `/help` регистронезависима, без аргументов (лишние — ошибка с использованием), без LLM, записи и usage; в опросе профиля и однократном запуске отклоняется, как другие команды. Однократный режим — та же шапка без строки команд, те же блоки без приглашения; флагов `--help` нет.

После ответа: «Ответ агента» (текст как есть) → «Предупреждение» (length и формат, оба возможны) → «Токены» → «Состояние задачи» для task-хода → приглашение. Блок — пустая строка, `── Заголовок ──`, пустая строка, тело; линий на всю ширину, рамок и префиксов строк нет, реплика пользователя не повторяется. Токены: `Оценка ≈ вопрос · контекст`, финальный вызов, рассуждение из генерации, summary и facts с итогом при вызове, `Ход · сессия` из `usage.turn` и `usage.session`; разряды через пробел (`formatCount`). Ошибки — stderr, `Ошибка · операция: причина`; ответ, предупреждения и сообщения — stdout. Зелёное подтверждение — только после успешной операции; «уже», «не найдена», «нечего» — обычный текст.

Состояние задачи строится только из TaskView: «Планирование (planning)», «Выполнение (execution)», «Проверка результатов (validation)», «Завершена (done)», отдельная строка `На паузе`, прогресс шагов и `Далее →` с приоритетом ожидаемого действия статуса (подсказка, не обещание модели). План: `[x]` выполнен, `[>]` текущий в execution, `[ ]` остальные. Профиль, working и long — пары `ключ: значение`, short — JSON, ветки — `*` и «активная».

Цвет — `styleText` из `node:util` с фактическим потоком `{ stream }`, без `validateStream: false` и глобального включения: заголовки голубые полужирные, профиль и приглашение фиолетовые, действие, пауза и предупреждения жёлтые, успех и done зелёные, ошибки красные, метрики серые; ответ модели не окрашивается, у каждого цвета есть текстовая подпись. Решение отдельно для stdout и stderr по правилам Node: TTY, `NO_COLOR`, `NODE_DISABLE_COLORS`, `FORCE_COLOR`. Тесты CLI убирают эти переменные через `vi.stubEnv` и восстанавливают `vi.unstubAllEnvs`, e2e удаляет их из окружения процесса.


Нужен Node.js 24+. Относительные импорты используют расширение `.ts`; сборка переписывает его в `.js`.

Тесты не вызывают внешний API и не используют локальную историю. `tests/support/fake-client.ts` проверяет параметры SDK; e2e использует подменённый `fetch`, временные директории и отдельные процессы для проверки восстановления контекста, памяти, задачи и выбранного профиля между процессами и режимами, а также повтора при нарушении инвариантов.
