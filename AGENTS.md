# AGENTS.md

## Что это

`my-first-agent` — stateful CLI-агент для DeepSeek через OpenAI-совместимый SDK. Линтер и форматтер — Biome, тесты — Vitest, CI — GitHub Actions.

## Учебный подход

Цель курса — научиться создавать собственных агентов. Приоритет — простая, понятная реализация, которая раскрывает изучаемое поведение и выполняет задание с учётом уточнений ментора.

- Для нового задания сначала определить учебную цель и минимально достаточный результат. Дополнительные улучшения отделять от обязательной части.
- Развивать существующего агента небольшими изменениями. Новые зависимости, абстракции, универсальные механизмы и инфраструктуру добавлять только при конкретной необходимости текущего задания.
- Если требования допускают приближение, использовать простые эвристики, искусственные ограничения и тестовые данные. Явно обозначать оценки и симуляции, отличая их от измерений и поведения реального API.
- Сравнения сценариев использовать для проверки и понимания поведения. Отдельные программы экспериментов, отчёты и демонстрационные системы создавать, только если они нужны по заданию.
- Если достаточно показать ошибку и её причину, автоматическое восстановление не входит в минимальную реализацию. Простота не отменяет корректность состояния, существующие инварианты и содержательные тесты.
- В объяснениях связывать изменение с тем, чему оно учит при создании агента. Подтверждённые ответы ментора использовать как ориентир по масштабу; точные требования нового задания имеют приоритет, неполученные ответы не считать согласованными.

## Архитектура

`src/index.ts` собирает приложение: окружение, SDK, `JsonHistoryRepository`, `Agent` и CLI. Репозиторий получает абсолютный путь к `process.cwd()/.agent-history.json`. Оба режима CLI используют этот файл. `src/cli.ts` работает только с интерфейсом `AgentPort` и не знает формат API или хранилище.

`src/agent.ts` владеет конфигурацией, историей и расходом токенов. При переданном `HistoryRepository` история загружается один раз в конструкторе после проверки конфигурации. `src/tokens.ts` содержит чистые функции оценки текста и стека по длине `content`. Перед каждым вызовом LLM агент оценивает подготовленные сообщения и проверяет `maxInputTokens`. `respond()` готовит кандидат summary и хвоста, вызывает LLM, учитывает usage, проверяет ответ, сохраняет всё состояние, затем обновляет память. `reset()` сначала сохраняет `{ summary: null, messages: [] }`, затем очищает память и статистику, сохраняя конфигурацию.

`src/history.ts` содержит `HistoryMessage`, `HistoryState` (`summary: string | null`, `messages: HistoryMessage[]`) и синхронный контракт `HistoryRepository` с `load()` / `save()`. `src/json-history-repository.ts` проверяет JSON через Zod и порядок пар, сохраняет через временный файл рядом с основным и `renameSync`. Агент зависит только от контракта и без репозитория работает в памяти.

Настройки одного агента находятся в `AgentConfig`. Сравнение моделей, повторные прогоны и внешние judge относятся к orchestration и не должны попадать в `Agent`.

## Инварианты

- В истории хранятся только завершённые пары `user`/`assistant`; непустой ответ с `validation.ok === false` также сохраняется.
- При загрузке и сохранении агент копирует массив и объекты сообщений, не разделяя изменяемую историю с репозиторием.
- Ошибка сохранения не меняет историю в памяти; usage состоявшегося API-вызова учитывается. Автоматического повторного вызова LLM нет.
- Ошибка сохранения пустого состояния при сбросе сохраняет прежние summary, сообщения и статистику; успешный сброс оставляет `{ summary: null, messages: [] }`.
- Только `ENOENT` означает пустую историю. Другие ошибки загрузки прерывают запуск, не меняя файл; ошибки содержат причину и путь, без диалога и стека.
- Конфигурация, ключ, оценки токенов и usage не сохраняются. После перезапуска восстанавливаются summary и сообщения, статистика начинается с нуля.
- Системный промпт собирается заново для каждого вызова и в историю не записывается.
- `tokenEstimate` измеряет новый вопрос после `trim()` и стек финального вызова до генерации. `usage.summaryCall`, `finalCall`, `turn` и `session` возвращаются отдельными снимками; reasoning входит в генерацию.
- `maxInputTokens: null` отключает локальный бюджет входа. Превышение блокирует вызов до API, не меняет историю и освобождает busy; равенство разрешено. Расход состоявшихся summary и подготовки meta сохраняется при блокировке следующего вызова. Успешный сброс сохраняет лимит.
- Meta-промпт остаётся внутренним и не попадает в историю диалога.
- Usage пустого ответа учитывается; ошибка транспорта без ответа usage не меняет.
- Параллельные вызовы одного stateful-агента запрещены.
- API-ключ не входит в `AgentConfig` и не возвращается в `AgentResult`.

Один файл рассчитан на один пишущий процесс: атомарная замена не разрешает конфликты двух CLI. История загружается целиком; старый префикс периодически заменяется summary с возможной потерей деталей. Нет полного архива, разбиения слишком длинной суммаризации, автоматического восстановления, нескольких диалогов, поиска, SQLite, версий формата, блокировок и сохранения usage.

## Периодическое сжатие

`historyCompressionEnabled` / `AGENT_HISTORY_COMPRESSION` по умолчанию `true`; `historyKeepLastMessages` / `AGENT_KEEP_LAST_MESSAGES` — `10`. Пустое окружение использует defaults, неверное непустое значение — ошибка. N проверяется и в `Agent`: положительное чётное безопасное целое, число сообщений, не пар.

Перед новым вопросом при `messages.length >= N + 10` весь префикс кроме последних N сообщений сжимается одним запросом той же модели. Порция накопления — константа 10. При N=10 сжатие перед вопросами 11, 16, 21. Summary получает только предыдущее summary и вытесняемый префикс, с `max_tokens: 512`, thinking disabled, без meta и политики финального ответа. Пустое или усечённое summary отклоняется после учёта usage.

Контекст: system → явно обозначенное summary как данные в user-сообщении → хвост → новый вопрос. Meta и финальный вызов используют один кандидат. `busy` охватывает весь ход; при любой ошибке кандидат не фиксируется, usage полученных ответов остаётся. Бюджет проверяется перед summary, meta и финальным вызовом. `summaryCall` равен null без сжатия; `turn` включает summary + meta + финальный вызов, `finalCall` — только финальный.

JSON хранит `{ summary, messages }`; старый массив читается как `{ summary: null, messages: массив }` без перезаписи при чтении. Следующий успешный save записывает объект. Выключение сжатия сохраняет использование существующего summary и не восстанавливает удалённые сообщения. Сценарий реального сравнения и результаты находятся в README; fake summary проверяет управление состоянием, а не качество модели.

## Команды

```bash
npm install
npm run dev
npm run dev -- "вопрос"
npm run lint
npm run typecheck
npm test
npm run test:coverage
npm run build
```

Нужен Node.js 24+. Относительные импорты используют расширение `.ts`; сборка переписывает его в `.js`.

Тесты не вызывают внешний API и не используют пользовательскую историю. `tests/support/fake-client.ts` проверяет параметры SDK; e2e использует подменённый `fetch`, временные директории и отдельные процессы для проверки восстановления контекста между режимами.
