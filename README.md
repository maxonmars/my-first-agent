# my-first-agent

Stateful CLI-агент для DeepSeek через OpenAI-совместимый API. Агент хранит диалог, рабочую и долговременную память, работает в выбранном вручную профиле агента (роль, ограничения, стиль) с общей для всех профилей памятью, ведёт текстовую задачу по этапам с сохранением прогресса, формирует запросы, проверяет ответы и считает токены; CLI отвечает за ввод и отображение результата.

## Подготовка и запуск

Нужен Node.js 24+.

```bash
npm install
cp .env.example .env
```

Добавьте `DEEPSEEK_API_KEY` в `.env`. Необязательный `DEEPSEEK_MODEL` по умолчанию равен `deepseek-v4-flash`. Файлы окружения, локальной истории, памяти и профилей исключены из Git.

```bash
npm run dev -- "Почему небо синее?"
npm run dev
```

Один запрос и интерактивный диалог используют историю выбранного режима и общие словари памяти. CLI показывает активный профиль и режим при запуске, после ответа — сам ответ, предупреждения, токены и состояние задачи отдельными блоками (см. [Вывод CLI](#вывод-cli)).

В интерактивном режиме `/help` показывает все команды по группам, `/exit` завершает диалог, `/reset` очищает диалог выбранного режима и статистику, сохраняя рабочую и долговременную память, профили и задачу. В Branching сброс удаляет все его ветки и checkpoint, оставляя пустую `main`. Команды доступны только в интерактивном режиме: однократный аргумент, начинающийся с `/`, в том числе `/help`, завершает запуск с кодом 1 без вызова модели.

## Вывод CLI

Интерактивный запуск начинается с короткой шапки: название, активный профиль или «без профиля», стратегия контекста и активная ветка Branching, строка `Команды: /help · /task · /memory · /profile`, состояние задачи, если она есть, и приглашение. Полная справка не печатается автоматически: `/help` выводит её группами «Диалог», «Задача», «Память», «Профиль», «Ветки». Команда регистронезависима, аргументов не принимает, не вызывает модель, ничего не записывает и не меняет статистику; во время `/profile-init` она, как и другие команды, не выполняется. Однократный запуск показывает ту же шапку без строки команд и те же блоки без приглашения.

После ответа вывод разделён на блоки с короткими заголовками, между блоками — одна пустая строка. Реплика пользователя повторно не печатается:

```text
редактор [задача] > Продолжай

── Ответ агента ──

Короткий текст клиенту без сроков и компенсации.

── Токены ──

Оценка ≈ вопрос 3 · контекст 1 292
API, финал: вход 1 594 · генерация 349
Из генерации: рассуждение 71
Ход 1 943 · сессия 1 943

── Состояние задачи ──

Проверка результатов (validation)
Шаги: 2/2 выполнены. Ожидается проверка.
Далее → отправьте «Проверь результат»

редактор [задача] >
```

1. «Ответ агента» — полный текст модели без изменений: переносы, списки, код и Markdown сохраняются, длинные строки переносит терминал.
2. «Предупреждение» — только при необходимости: генерация остановилась по лимиту длины, формат не выдержан; оба предупреждения могут быть в одном блоке.
3. «Токены» — всегда: оценки со знаком `≈`, provider usage финального вызова и рассуждение как часть генерации, строки `API, summary` и `API, facts` с итогом при их вызове, расход хода и сессии из `usage.turn` и `usage.session`. Разряды чисел разделяются пробелом.
4. «Состояние задачи» — после хода задачи; в обычном чате и на паузе его нет.

Ошибки запросов и команд идут в stderr строкой `Ошибка · Запрос не удался: причина` или `Ошибка · Команда не выполнена: причина`, без стека. Ответы, предупреждения и сообщения — в stdout. Подтверждение выводится только после успешной операции; ответы без изменений вроде «Задача уже на паузе» или «Запись не найдена» успехом не выделяются. `/memory` и `/profile` показывают словари и профиль парами `ключ: значение`, `short` — JSON, `/profile list` и `/branches` — списки профилей и веток с пометкой активного элемента.

Цвет — встроенный `util.styleText`, без зависимостей. Голубые полужирные заголовки блоков, фиолетовые профиль и приглашение, жёлтые следующее действие, пауза и предупреждения, зелёные успех операции и завершённая задача, красные ошибки, серые метрики и подписи. Ответ модели выводится цветом терминала. Каждый цвет сопровождается текстовой подписью, поэтому без цвета смысл сохраняется.

Поддержка цвета определяется отдельно для stdout и stderr по правилам Node.js. Без `FORCE_COLOR` цвет включается только в терминале с поддержкой цвета; `NO_COLOR`, `NODE_DISABLE_COLORS` или `TERM=dumb` его отключают. `FORCE_COLOR` важнее: `0` отключает цвет, `1`, `2` или `3` включают его и при выводе в файл или pipe. Оформление не попадает в историю, память, профиль и задачу.

## Профили агента

Профиль агента задаёт роль, подход, стиль и ограничения работы. Один агент с общей историей, памятью, задачей и статистикой переключается между профилями вручную: выбранная роль действует со следующего ответа до явной смены командой.

| Группа | Содержимое |
| --- | --- |
| `style` | Тон, подробность, язык, оформление результата: списки, таблицы, структура |
| `constraints` | Рабочие правила: что не добавлять и не менять, как обозначать предположения, границы роли |
| `context` | Роль, предметная область, типичные задачи и критерии качества результата |

Конкретные сведения текущей работы — дата мероприятия, аудитория, длительность, согласованные решения — задаются в диалоге или рабочей памяти.

### Создание и выбор

```text
/profile-init
```

CLI спрашивает идентификатор профиля (`profileId`, например `аналитик`, `автор` или `редактор`), затем по одному вопросу на группу с подсказкой и прежним значением. Опрос фиксированный, не вызывает модель, не попадает в историю и не расходует токены.

- Существующий профиль берётся как черновик; пустой ответ сохраняет прежнее значение, для нового профиля — пропускает группу.
- Неверный идентификатор повторяет вопрос. `/cancel` отменяет опрос, `/exit` и конец ввода завершают CLI без сохранения; другие команды во время опроса не выполняются.
- После третьей группы профиль сохраняется и выбирается одной записью каталога. Если запись не удалась, остаётся прежний профиль.

`profileId` — локальный ключ: 1–64 символа, буквы, цифры, дефис или подчёркивание, первый символ — буква или цифра. Крайние пробелы обрезаются, регистр важен: `автор` и `Автор` — разные профили.

| Команда | Действие |
| --- | --- |
| `/profile` | Показать активный профиль парами `группа: значение` |
| `/profile list` | Показать идентификаторы сохранённых профилей, активный отмечен `*`; пустой каталог — подсказка `/profile-init` |
| `/profile load profileId` | Выбрать существующий профиль; действует со следующего ответа |
| `/profile set style\|constraints\|context значение` | Заменить группу; значение — остаток строки |
| `/profile delete style\|constraints\|context` | Удалить группу; если её нет, файл не пишется |
| `/profile clear` | Очистить настройки активного профиля, сохранив его идентификатор и всё общее состояние |

`/profile list` сортирует идентификаторы по кодам символов, не вызывает модель и ничего не записывает. Без выбранного профиля команды изменения предлагают `/profile-init`. Команды и группы регистронезависимы; однократный запуск с командой завершается кодом 1 без вызова модели.

```text
── my-first-agent ──

Профиль: аналитик
Контекст: sliding
Команды: /help · /task · /memory · /profile

аналитик > /profile list

── Профили ──

- автор
* аналитик — активный
- редактор

аналитик > /profile load редактор
Профиль: редактор
Контекст: sliding

редактор >
```

С задачей приглашение — `редактор [задача] > ` или `редактор [чат, задача на паузе] > `. Без выбранного профиля в шапке — `Профиль: без профиля`, приглашение — `без профиля > `.

### Общая память и один агент

История всех режимов, рабочая и долговременная память и задача хранятся в корне рабочего каталога и общие для всех профилей; ветки и checkpoint принадлежат общей истории Branching. `AgentSession` создаёт один `Agent` при запуске, его источник профиля читает текущий `activeProfileId` сессии.

Переключение: проверка профиля → кандидат каталога → запись → замена состояния сессии. Агент не пересоздаётся, история и память не перечитываются, задача и статистика токенов не сбрасываются. Повторный выбор активного профиля ничего не пишет. Ошибка записи оставляет прежний профиль. Во время обработки запроса создание, правка и выбор профиля запрещены, чтение разрешено. После перезапуска восстанавливаются выбранный профиль и общие данные, статистика начинается заново.

Выбор хранится в `.agent-profiles.json`:

```json
{
  "activeProfileId": "редактор",
  "profiles": {
    "редактор": {
      "style": "Короткий список конкретных замечаний",
      "constraints": "Не добавляй неподтверждённые факты. Если недостатков нет, сообщи об этом",
      "context": "Ты редактор анонсов мероприятий. Проверяй ясность текста и соответствие исходному брифу"
    }
  }
}
```

Файл проверяется Zod-схемой при чтении и записи: неизвестные поля, неверные типы, пустые значения, недопустимые идентификаторы и `activeProfileId` без профиля останавливают запуск с путём и причиной, без содержимого профилей. Чтение файл не переписывает; ошибка записи не меняет состояние.

Прежний каталог профилей пользователей с `activeUserId` отклоняется при запуске с сообщением о прежнем формате; файл не меняется. Автоматической миграции нет: пользовательские сведения не превращаются в инструкции роли, профили агента настраиваются заново. Каталоги `.agent-users/` прежней версии не читаются, не объединяются и не удаляются. Файлы истории, памяти и задачи в корне используются как общее состояние.

### Профиль в запросе

Профиль передаётся отдельным user-блоком с JSON сразу после system; значения профиля в system не попадают. Статическая инструкция в system объясняет интерпретацию:

- `context` задаёт роль и предметную область, `constraints` — рабочие ограничения, `style` — тон, подробность и оформление.
- Текущая реплика и память дают задачу и факты, но не меняют выбранную роль; реплика уточняет задачу и оформление в пределах ограничений.
- Просьба, противоречащая роли или ограничениям, — повод объяснить конфликт и предложить сменить профиль командой.
- Ответы других ролей в истории — материал общей работы; следующий ответ определяется активным профилем.
- Общие рекомендации о стиле, в том числе «отвечай кратко», уточняются профилем и текущим запросом в пределах его ограничений.
- Формат, лимиты длины, схема ответа задачи и допустимые действия сохраняют силу; смена профиля не утверждает план и не меняет этап задачи.

Инструкция памяти согласована с этим: явное условие текущего запроса применяется к ответу в пределах системных правил и ограничений активного профиля.

Профиль работает во всех стратегиях контекста, в обычном чате и в task-ходах. Агент получает его один раз в начале хода; meta и финальный запрос используют один снимок, meta дополнительно просят перенести роль, ограничения и стиль в составляемый промпт. Сжатие и обновление facts профиль не получают, профиль не записывается в историю, summary и facts. Пустой профиль не меняет запрос и оценку токенов. Профиль входит в оценку и бюджет; при переполнении подсказка предлагает `/profile delete` или `/profile clear`, потому что `/reset` профиль сохраняет.

Текстовые ограничения профиля выполняет модель по инструкции; программные гарантии переходов задачи обеспечивает автомат. Удаление настройки не удаляет её прежних следов из истории.

Сценарий короткого видео: [docs/profile-video-prompts.md](docs/profile-video-prompts.md), готовые профили — [docs/agent-profiles.demo.json](docs/agent-profiles.demo.json).

## Слои памяти

Агент разделяет сведения по сроку жизни и по тому, кто их изменяет. Все слои хранятся в корне рабочего каталога и общие для всех профилей агента.

| Слой | Содержимое | Кто изменяет | Хранение в каталоге данных | Когда очищается |
| --- | --- | --- | --- | --- |
| `short` | Состояние диалога выбранной стратегии: сообщения, summary, facts, ветки, checkpoint | Обработка ходов, `/reset`, команды веток | Файл истории режима | `/reset` или `/memory clear short` |
| `working` | Цель, ограничения, параметры и решения текущей задачи | Только команды `/memory` | `.agent-memory.working.json` | `/memory clear working` |
| `long` | Сведения, предпочтения, сохранённые знания и решения | Только команды `/memory` | `.agent-memory.long-term.json` | `/memory clear long` |

Все три слоя восстанавливаются после перезапуска; статистика расхода начинается с нуля.

**Стратегия контекста** определяет, как обрабатывается `short`: полная история, summary, окно, facts или ветки. **Рабочая и долговременная память** от стратегии не зависят и отдельного переключателя не имеют: непустые словари добавляются к запросу в любом режиме. Facts — автоматически извлечённая производная диалога и относятся к `short`; их обновление не пишет в `working` или `long`, прежние facts в словари не переносятся. Автоматического распределения сведений по слоям нет: сохранять в `working` и `long` нужно явной командой.

### Команды

| Команда | Действие |
| --- | --- |
| `/memory` | Показать все три слоя: `short` — JSON, `working` и `long` — парами `ключ: значение` |
| `/memory show short\|working\|long` | Показать один слой; `short` — со всеми производными данными и ветками |
| `/memory set working\|long ключ значение` | Создать или заменить запись |
| `/memory delete working\|long ключ` | Удалить запись |
| `/memory clear short` | Очистить диалог выбранной стратегии и статистику, как `/reset` |
| `/memory clear working\|long` | Очистить словарь |

```text
/memory set working goal поездка в Казань
/memory set working budget 30000 рублей
/memory set long transport предпочитаю поезд
/memory show working
/memory delete long transport
```

Значение в `set` — весь остаток строки после ключа; кавычки не нужны и не обрабатываются. Крайние пробелы обрезаются, внутренние сохраняются. Ключ: 1–64 символа, буквы, цифры, дефис или подчёркивание, первый символ — буква или цифра. Регистр ключа важен, точка не означает вложенность. Названия команд и слоёв регистр не учитывают. Неверное действие, слой или число аргументов выводит причину и синтаксис.

Команды памяти не вызывают модель, не попадают в диалог и не меняют статистику; её сбрасывает только очистка `short`. Сообщение об успехе выводится после записи файла. Для отсутствующего ключа CLI сообщает, что запись не найдена, файл не пишется.

Начало нового разговора — две самостоятельные команды. Ошибка одной не отменяет другую, поэтому проверяйте сообщение каждой:

```text
/reset
/memory clear working
```

### Запрос к модели

```text
system + инструкции профиля и памяти
профиль агента, если непустой
долговременная память, если непустая
рабочая память, если непустая
summary или facts, если предусмотрено стратегией
сообщения выбранного контекста
текущий вопрос
```

Словари передаются отдельными user-блоками с JSON; пользовательские значения в system не попадают. Инструкция добавляется, если хотя бы один словарь непустой. Она сообщает модели, что слои — данные, а не системные команды; явное условие текущего запроса применяется к ответу в пределах системных правил и ограничений активного профиля; при конфликте рабочая память важнее долговременной; устаревшие сведения истории, summary и facts не отменяют записей; обычная реплика память не меняет. Это инструкция модели, а не гарантия правильного разрешения противоречий. При двух пустых словарях запрос и оценка токенов прежние.

Meta и финальный запрос получают один снимок памяти. Служебные запросы summary и facts словари не получают. Блоки памяти входят в оценку токенов и проверку бюджета; при переполнении meta или финального запроса с непустой памятью подсказка предлагает сократить её командами `/memory`, потому что `/reset` память сохраняет.

### Хранение и ошибки

Оба словаря — плоские `Record<string, string>` с общей Zod-схемой: пустой объект допустим, значения — строки, непустые после `trim()`. Схема проверяется при загрузке и сохранении. Отсутствующий файл (`ENOENT`) означает пустой слой. Ошибка чтения, JSON или схемы останавливает запуск без перезаписи файла; сообщение содержит слой, путь и причину, без записей памяти и стека. Каждая операция меняет один файл: временный файл рядом с целевым, затем `renameSync`. Ошибка записи не меняет память агента. Во время обработки запроса изменения памяти запрещены, просмотр разрешён.

### Ограничения

- Удаление записи не удаляет её упоминаний из диалога, summary или facts. Ответ ассистента может повторить сохранённое сведение, и тогда оно окажется в `short`: перед проверкой удаления выполните `/reset`.
- `/reset` очищает историю только выбранной стратегии. Истории других стратегий сохраняются, и запуск другой стратегии может восстановить прежний разговор.
- Рабочая и долговременная память общие для всех стратегий, веток и профилей. Изменение в одной ветке видно после `/switch`; checkpoint и переключение ветки словари не копируют и не откатывают.
- Одна текущая задача на рабочий каталог, один пишущий процесс на рабочий каталог. Межфайловых транзакций, автоматического ограничения размера словарей и поиска нет.

Сценарий короткого видео: [docs/memory-video-prompts.md](docs/memory-video-prompts.md).

## Задача: конечный автомат

Задача ведёт одну текстовую работу по этапам `planning → execution → validation → done`. Агент знает текущий этап и шаг, хранит план, полные результаты шагов, открытый вопрос и последнюю проверку, показывает ожидаемое действие и продолжает после паузы или перезапуска без повторного объяснения.

| Механизм | Что хранит | Кто меняет |
| --- | --- | --- |
| Обычный чат (`short`) | Историю выбранной стратегии контекста | Каждый ответ вне задачи, `/reset` |
| `working` и `long` | Словари условий и сведений | Только команды `/memory` |
| Стратегия контекста | Способ обработки обычного чата: полная история, summary, окно, facts, ветки | Переменная `AGENT_CONTEXT_STRATEGY` |
| Задача | Описание, этап, пауза, план, результаты, вопрос, проверка и собственная переписка | Код автомата по командам `/task` и действиям модели |

Пока задача есть и не на паузе, обычные реплики относятся к ней, включая этап done — для обсуждения результата. Без задачи или на паузе агент работает как прежде.

### Команды

| Команда | Действие |
| --- | --- |
| `/task` | Показать описание, план с отметками шагов, результаты, замечания проверки, вопрос агента, этап, паузу и следующее действие |
| `/task start описание` | Создать задачу на этапе planning; описание — остаток строки |
| `/task approve` | Утвердить предложенный план: только planning, без паузы и открытого вопроса |
| `/task pause` | Приостановить задачу на любом этапе; реплики идут в обычный чат |
| `/task resume` | Вернуть реплики в задачу и показать место продолжения |
| `/task clear` | Удалить задачу; обычный диалог, профиль, память и статистика сохраняются |

Команды не вызывают модель, не попадают в переписку и не расходуют токены. Имена команд регистронезависимы, регистр и внутренние пробелы описания сохраняются, кавычки не разбираются. Лишние аргументы, пустое описание и отсутствие задачи для `approve`, `pause`, `resume` выводят причину. Незавершённую задачу, в том числе на паузе, заменить нельзя — сначала `/task clear`; завершённую можно заменить новой. Повторные `pause`, `resume` и `clear` без задачи ничего не записывают.

`/task start` только создаёт задачу. Работу модели запускает следующая обычная реплика, например «Продолжай»; первый шаг после `/task approve` — тоже. Словесное «утверждаю» план не утверждает: модель должна объяснить, что нужна команда.

При запуске, после команд задачи и после каждого хода задачи CLI показывает блок «Состояние задачи», а приглашение — куда пойдёт реплика:

```text
── Состояние задачи ──

Выполнение (execution)
Шаги: 1/2 выполнены. Сейчас шаг 2 из 2: Подготовить текст клиенту
Далее → продолжите шаг 2, например репликой «Продолжай»

без профиля [задача] >
```

Блок строится только из сохранённого состояния задачи, а не из текста ответа: фраза модели «Задача выполнена» не делает этап done. Этапы подписаны как «Планирование (planning)», «Выполнение (execution)», «Проверка результатов (validation)» и «Завершена (done)». Строка `Далее →` подсказывает следующую реплику в порядке ожидаемого действия: на паузе — `/task resume`; при открытом вопросе — ответить на него; в planning с планом — `/task approve` или просьба изменить план; в planning без плана — уточнить условия или попросить план; в execution — продолжить текущий шаг, например «Продолжай»; в validation — «Проверь результат», в том числе после исправлений по замечаниям; в done обязательных действий нет. Это подсказка, а не обещание действия модели или автоматического перехода.

На паузе в блоке есть отдельная строка `На паузе`, подсказка `Далее → /task resume, …` объясняет, что реплики сейчас идут в обычный чат, приглашение — `без профиля [чат, задача на паузе] > `. Сообщения `/task pause` и `/task resume` называют, куда пойдут следующие реплики. Без задачи блока нет, приглашение прежнее.

Черновик плана, ожидающий утверждения, CLI выводит из сохранённого состояния внутри блока — после хода задачи, при запуске и после `/task resume`; модель не обязана повторять шаги в `answer`. При запуске и после `/task resume` так же выводится открытый вопрос агента:

```text
Планирование (planning)
План на утверждение:
  [ ] 1. Определить допустимое содержание ответа
  [ ] 2. Подготовить текст клиенту
Далее → /task approve или попросите изменить план
```

```text
Планирование (planning)
На паузе
Сбор требований.
Вопрос агента: Какой номер заказа?
Далее → /task resume, чтобы вернуться к задаче; сейчас реплики идут в обычный чат
```

Полный `/task` выводит отдельные блоки «Описание задачи», «План», «Результаты шагов», «Проверка», «Вопрос агента» и в конце «Состояние задачи»; план и вопрос показываются по одному разу, результаты — полностью. В плане `[x]` — выполненный шаг, `[>]` — текущий шаг на этапе execution, `[ ]` — остальные.

### Переходы

| Переход | Когда |
| --- | --- |
| planning → execution | `/task approve` при готовом плане |
| execution → validation | Модель сдала результат последнего шага; проверка выполняется по следующей реплике |
| execution → planning | Модель вернула `replan`: план, результаты, вопрос и проверка очищаются, новый план снова утверждается |
| validation → done | Модель подтвердила выполнение требований |
| validation → execution | Модель вернула замечания и номер шага; результаты с этого шага удаляются и выполняются заново |

Из done переходов нет. Уточнения и обсуждения оставляют этап прежним, пауза меняет только признак `paused`. Этап, номер шага и результаты назначает код: модель не возвращает состояние и не переписывает прежние результаты. Результаты всегда соответствуют началу плана без пропусков.

Ожидаемое действие вычисляется по порядку: пауза → возобновить; открытый вопрос → ответить; planning с планом → утвердить; planning без плана → уточнить условия или составить план; execution → продолжить шаг; validation → запустить проверку; done — обязательных действий нет.

### Протокол ответа модели

Финальный запрос задачи всегда использует JSON mode. Модель возвращает `answer` и одно действие; пользователю и в переписку попадает только `answer`.

| Действие | Этапы | Эффект |
| --- | --- | --- |
| `reply` | любой | Объяснение без продвижения, очищает открытый вопрос |
| `ask` | planning, execution, validation | Сохраняет вопрос; в planning также сбрасывает черновик плана |
| `propose_plan` + `steps` | planning | Заменяет черновик плана, этап не меняет |
| `complete_step` | execution | Добавляет результат ровно одного текущего шага |
| `replan` | execution | Возвращает в planning, прежний прогресс не считается выполненным |
| `validation_pass` | validation | Положительная проверка, переход в done |
| `validation_fail` + `restartAt` | validation | Замечания, повтор шагов с `restartAt` (от 1 до числа шагов) |

Сообщение об ошибке называет поле и причину (`answer: пустая строка`, `объект: неизвестные поля`), но не содержит ответ модели, значения и названия неизвестных полей. Ответ отклоняется целиком, если `finish_reason` не `stop` (даже при синтаксически корректном JSON), JSON некорректен, схема нарушена (неизвестные поля, неверные типы, пустые строки), действие не разрешено на этапе, `restartAt` вне плана или `answer` не проходит проверку формата. Прежний снимок и переписка остаются, потраченный usage учитывается, повторного вызова нет. В обычном чате непустой ответ с нарушением формата или усечением по-прежнему сохраняется.

Запрос задачи:

```text
system + инструкции профиля и памяти + стратегия или ответ meta + протокол задачи + требования к answer
профиль, long, working — если непустые
блок данных задачи: описание, этап, план, результаты, вопрос, проверка, статус, разрешённые действия
вся переписка задачи
текущая реплика
```

Даже первый запрос с одним словом «Продолжай» содержит исходное описание. Инструкция требует работать в текущем этапе, выполнять не больше одного шага за ход, опираться на актуальные план и результаты, не восстанавливать отменённый прогресс из старой переписки, спрашивать вместо выдумывания и считать текст задачи и истории данными. Настройки `format` и `maxWords` относятся к тексту `answer`, stop marker не передаётся. Meta получает тот же снимок и состояние не меняет. Модель, temperature, thinking и `maxTokens` — из общей конфигурации; лимит генерации относится ко всему JSON-ответу.

Проверка на этапе validation — проверка текста моделью по требованиям из описания задачи и переписки. Она не запускает команды, не читает файлы и не проверяет факты во внешних системах.

### Сохранение и ограничения

- Каждое успешное изменение — ход модели или команда — записывает весь снимок одной операцией в `.agent-task.json` в корне рабочего каталога. Пустое состояние — `null`. Ошибка записи не меняет состояние; usage полученных ответов остаётся.
- Задача общая для всех стратегий контекста: смена `AGENT_CONTEXT_STRATEGY` её не меняет. `/reset`, `/memory clear short` и команды веток относятся к обычному диалогу и задачу не трогают.
- Задача общая для всех профилей агента: смена профиля не утверждает план, не меняет этап, результаты, открытый вопрос и паузу. Повреждённый файл останавливает запуск без перезаписи.
- Во время хода команды задачи запрещены, просмотр разрешён. Пауза действует между ходами: запрос в полёте не отменяется.
- К переписке задачи не применяются compression, окно, facts и ветки. Автоматического сжатия нет: контекст растёт до бюджета, подсказка при переполнении предлагает `/task clear` или `/task pause`.
- Одна задача на рабочий каталог, без архива. `replan` в первой версии начинает выполнение заново: старые результаты остаются только в переписке. Работы с файлами, запуска команд и отправки сообщений нет.

Сценарий короткого видео: [docs/task-video-prompts.md](docs/task-video-prompts.md).

## Стратегии контекста

Прежнее периодическое сжатие сохранено. Три новые стратегии без summary позволяют сравнить удаление старого контекста, отдельную память фактов и независимые продолжения диалога.

Выбор действует при запуске, через окружение или `.env`:

```bash
AGENT_CONTEXT_STRATEGY= npm run dev
AGENT_CONTEXT_STRATEGY=compression npm run dev
AGENT_CONTEXT_STRATEGY=sliding npm run dev
AGENT_CONTEXT_STRATEGY=facts npm run dev
AGENT_CONTEXT_STRATEGY=branching npm run dev
```

Пустое значение, пробелы или отсутствие `AGENT_CONTEXT_STRATEGY` означают полную историю без обработки контекста (`contextStrategy: null`). Неизвестное непустое значение — ошибка. Обычный режим и `compression` продолжают один диалог в `.agent-history.json`; у `sliding`, `facts`, `branching` свои истории. `AGENT_HISTORY_COMPRESSION` больше не читается: оставшуюся переменную в старом `.env` можно удалить.

| Режим | Что сохраняется | Стек для ответа |
| --- | --- | --- |
| Без стратегии (пусто) | Вся доступная история и прежнее summary, если есть | System + прежнее summary + вся история + новый вопрос |
| Compression | Summary + несжатый хвост | System + summary как данные + хвост + новый вопрос |
| Sliding Window | Последние N сообщений | System + N сообщений + новый вопрос |
| Facts | Словарь ключ-значение + последние N сообщений | System + facts как данные + N сообщений + новый вопрос |
| Branching | Полные истории веток, checkpoint, активная ветка | System + история активной ветки + новый вопрос |

`AGENT_KEEP_LAST_MESSAGES=10` задаёт N: положительное чётное безопасное целое, **число сообщений, не ходов**. Один завершённый ход — два сообщения. Окно может быть короче N в начале диалога. N проверяется для всех конфигураций; в Compression задаёт сохраняемый хвост при сжатии, в Branching не ограничивает историю.

### Без стратегии — полная история

```dotenv
AGENT_CONTEXT_STRATEGY=
```

Сообщения сохраняются и отправляются целиком: без обрезания, извлечения facts, ветвления и новых summary. Контекст растёт до локального бюджета или лимита API. На чистой истории это system + весь диалог + новый вопрос. N в этом режиме не ограничивает историю.

Если диалог уже сжимался, прежнее summary остаётся частью контекста. Отключение стратегии не возвращает вытесненные сообщения и не удаляет сохранённые сведения. Для чистого диалога используйте `/reset`. Выбор `compression` возобновляет периодическое сжатие той же истории.

### Compression — прежний режим

```dotenv
AGENT_CONTEXT_STRATEGY=compression
```

Выбор `compression` включает сжатие без дополнительного флага. При `messages.length >= N + 10` перед новым вопросом весь префикс кроме последних N сообщений заменяется summary. Порция накопления — 10 сообщений. При N=10 сжатие происходит перед вопросами 11, 16, 21; после ответа сохраняются summary и N+2 сообщения, между сжатиями хвост растёт.

Служебный запрос получает только предыдущее summary и вытесняемый префикс. Используются та же модель, `max_tokens=512`, thinking disabled, без meta и политики финального ответа. Пустое или усечённое summary отклоняется после учёта usage. Meta и финальный запрос получают один кандидат summary и хвоста; сохранение происходит вместе с новой парой.

Чтобы отключить сжатие, оставьте `AGENT_CONTEXT_STRATEGY` пустым. В `sliding`, `facts` и `branching` суммаризация не выполняется.

### Sliding Window

Перед запросом выбираются последние N завершённых сообщений. После успешного ответа новая пара добавляется, сохраняются только последние N сообщений, включая эту пару. Старый префикс удаляется и из памяти, и из файла. Новый вопрос в API идёт сверх N; system не считается сообщением окна.

Если N уменьшили после перезапуска, более длинная история ограничивается при подготовке запроса и обрезается на диске после следующего успешного ответа. Полного архива нет.

### Sticky Facts / Key-Value Memory

После каждого нового сообщения пользователя модель обновляет весь JSON-словарь `Record<string, string>`. Например:

```json
{"project":"Север","budget":"96000 рублей","storage":"только локально"}
```

Служебный запрос получает прежний словарь, последние N сообщений и вопрос. Инструкция требует стабильных ключей, точных значений, замены исправленных фактов и удаления явно отменённых. Предложение ассистента становится договорённостью только после согласия пользователя. Zod проверяет словарь непустых строк; правильность извлечения зависит от модели.

Обновлённые facts допускают в ключах только латинские буквы, цифры, `_` и `-`, первый символ — латинская буква. Инструкция просит английские названия в snake_case, например `conversation_code`; язык значений сохраняется. Старые ключи на других языках загружаются без изменения файла и передаются модели для переименования при следующем обновлении. Ответ модели с недопустимым ключом отклоняется без сохранения хода.

JSON mode задаёт JSON-формат, но не проверяет схему словаря. Например, `{"budget":84000}` — корректный JSON, но facts требует `{"budget":"84000 рублей"}`. Инструкция содержит пример плоского словаря и требует записывать числа, даты и логические факты строками. При нарушении схемы ошибка показывает причину и полученный тип, без содержимого фактов; уточнение инструкции не гарантирует соблюдение схемы моделью.

Обновлённые facts используются уже в ответе на текущий вопрос. Они передаются отдельным user-блоком с пометкой «данные», не добавляются в system. Meta и финальный запрос получают один кандидат контекста. Facts и новая пара сохраняются вместе только после непустого финального ответа и успешной записи.

Извлечение использует ту же модель, JSON mode, `max_tokens=512`, thinking disabled, без настроек формата и ограничений финального ответа. При пустом ответе, усечении, некорректном JSON или неверной структуре ход завершается ошибкой; память не меняется, usage ответа учитывается. Автоматического повтора или восстановления нет. Словарь не имеет политики удаления по размеру: слишком большой результат или вход может привести к ошибке лимита.

### Branching

Начальная ветка — `main`. Доступны один checkpoint и именованные ветки:

```text
Общая цель проекта — локальный учёт заявок.
/checkpoint
/branch вариант-а
В этом варианте срок — 1 ноября.
/branch вариант-б
В этом варианте срок — 15 ноября.
/switch вариант-а
Какой срок выбран в этом варианте?
/branches
```

`/checkpoint` сохраняет копию активного диалога; повторная команда заменяет снимок. `/branch имя` создаёт ветку **из checkpoint**, даже если текущая ветка уже продолжена, и делает новую активной. `/switch имя` выбирает существующую ветку. `/branches` показывает число сообщений и помечает активную ветку `*` и подписью «активная».

Имена уникальны, 1–64 символа: буквы, цифры, дефис, подчёркивание; первый символ — буква или цифра. Повторное имя не перезаписывает ветку. Без checkpoint создать ветку нельзя. Команды доступны в интерактивном Branching, не обращаются к LLM и не расходуют токены.

В запрос входит полный диалог только активной ветки. Другие ветки и checkpoint в API не отправляются. История растёт до локального бюджета или предела провайдера. Объединения веток и дерева checkpoint нет.

## Сохранение между запусками

Каждый режим использует свой файл истории в рабочем каталоге `process.cwd()`; файлы общие для всех профилей агента. Каталог профилей — `process.cwd()/.agent-profiles.json`.

| Режим | Файл | Пустое состояние |
| --- | --- | --- |
| Без стратегии / Compression | `.agent-history.json` | `{"summary":null,"messages":[]}` |
| Sliding | `.agent-history.sliding.json` | `{"kind":"sliding","messages":[]}` |
| Facts | `.agent-history.facts.json` | `{"kind":"facts","messages":[],"facts":{}}` |
| Branching | `.agent-history.branching.json` | `{"kind":"branching","activeBranch":"main","branches":{"main":[]},"checkpoint":null}` |

Рабочая и долговременная память хранятся отдельно, в `.agent-memory.working.json` и `.agent-memory.long-term.json` того же каталога, и общие для всех режимов и профилей; пустой словарь сохраняется как `{}`. Задача с перепиской — в `.agent-task.json` того же каталога, тоже общая для всех режимов; без задачи файл отсутствует или содержит `null`.

Обычный режим и Compression используют прежний `.agent-history.json` и сохраняют прежний формат `{ summary, messages }`. Старый JSON-массив читается как сообщения с summary=null без перезаписи при загрузке; следующий успешный save пишет объект. Три новых режима используют свои файлы и не читают старую историю. Если формат загруженного состояния не соответствует выбранному режиму, запуск останавливается.

Репозиторий проверяет структуру при чтении и записи, завершённость и порядок пар во всех ветках и checkpoint, наличие `main` и активной ветки. `kind` обозначает формат данных. Конфигурация, API-ключ, system, внутренние запросы и usage не сохраняются. После перезапуска восстанавливаются данные и активная ветка, расход сессии начинается с нуля.

Изменения выполняются как кандидат → запись временного файла рядом с основным → `renameSync` → обновление состояния агента. Это относится также к checkpoint, созданию и переключению ветки, сбросу, командам памяти и задаче. При ошибке записи прежнее состояние остаётся, потраченные токены учитываются. `/reset` сохраняет пустое состояние, не удаляя файл, и не затрагивает другие режимы.

Только `ENOENT` означает отсутствие истории или словаря памяти. Повреждённый JSON или ошибка чтения останавливают запуск с причиной и путём, без содержимого диалога или памяти и без стека. Автоматического исправления файла нет. Один файл рассчитан на один пишущий процесс; атомарная замена не решает конфликт одновременных CLI.

## Токены и бюджет

`tokenEstimate.questionTokens` оценивает вопрос после `trim()`. `contextTokens` — весь стек финального запроса до генерации, включая блоки памяти. Оценка `Math.ceil(content.length / 4)` — эвристика по длине JavaScript-строк, без служебных надбавок; это не токенизатор DeepSeek. CLI выводит оценки в блоке «Токены» со знаком `≈`.

`usage.summaryCall` — расход сжатия или `null`, если его не было. `usage.factsCall` — расход обновления словаря или `null` в других режимах. В ходе задачи оба равны `null`. `finalCall` — только финальный запрос, `turn` — сумма summary + facts + meta + финального запроса, `session` — все полученные API-ответы текущего экземпляра агента. Reasoning уже входит в completion и повторно не прибавляется. При отсутствующем usage агент возвращает нулевой fallback, а не измеренный нулевой расход.

```dotenv
AGENT_MAX_INPUT_TOKENS=2000
```

Пустое или отсутствующее значение отключает бюджет. Иначе нужен положительный безопасный integer. Перед каждым API-вызовом, включая summary, извлечение facts и подготовку meta, оценивается подготовленный стек. Равенство лимиту разрешено; превышение не вызывает API, не меняет контекст и освобождает busy. Уже потраченный usage предыдущих вызовов остаётся.

Это учебный лимит входа: он не резервирует генерацию и не гарантирует принятия запроса провайдером. `maxTokens` ограничивает генерацию через `max_tokens`. Непустой усечённый **финальный** ответ сохраняется с предупреждением; усечённый ответ summary или извлечения facts отклоняется.

## Сравнение с реальной моделью

Сценарий выполнял 15 одинаковых пользовательских ходов на каждой стратегии. Branching проходит линейную часть в `main`. На пятом ходу сохраняется checkpoint для отдельной проверки веток.

| Ходы | Содержание |
| --- | --- |
| 1–4 | «Север», SN-047, Томск, локальный учёт заявок; 84000 рублей; 17 октября 2026; Ирина Белова; кедр-731; локальное хранение, запрет платных облаков, еженедельный email-отчёт |
| 5 | Бюджет исправлен на 96000 |
| 6–10 | Промежуточные вопросы; критерий — 12 обработанных заявок; кабинет 314 и trial-B9 |
| 11 | Контроль основных фактов и согласованных требований |
| 12 | Email-отчёт отменён |
| 13–14 | Приёмку проводит Павел Орлов; промежуточный вопрос |
| 15 | Итоговое ТЗ с действующими и отменёнными требованиями |

Перед прогоном фиксируется список проверки: на ходу 11 нужны все **14 фактов** из ходов 1–5, 7 и 10 с актуальным бюджетом; на ходу 15 те же факты с отменённым email-отчётом и добавленным приёмщиком (**15 пунктов**). Считаем явное воспроизведение, пропуски, противоречия и выдуманные значения. «Неизвестно» честнее выдуманного значения, но не считается сохранением факта.

Дополнительная проверка Branching: две ветки от checkpoint пятого хода, по пять реплик в каждой. В A срок 1 ноября, 3 участника; в B срок 15 ноября, 8 участников. После переключения в A запрашиваются её условия. Общий бюджет — 96000, координатор — Ирина Белова; email-отчёт в обеих ветках ещё действует, потому что отмена из `main` произошла после checkpoint. Чужие сроки и число участников не должны попадать в ответ. Токены этого эксперимента считаются отдельно.

### Условия

Реальные API-вызовы на вымышленных данных с отдельными чистыми историями. Условия: direct/text, температура 0, thinking disabled, одинаковый system, N=10, бюджет входа и лимиты финального ответа отключены. Facts дополнительно выполняет 15 служебных запросов. Детерминированность ответов при температуре 0 не гарантируется.

Расход суммировался по `usage.turn.totalTokens` отдельно для линейной части и дополнительных веток; сессионные снимки складывать нельзя, в Branching они включают оба эксперимента. Стоимость facts входит в итог. При отсутствии provider usage измерение неполное. Уменьшение одного входного запроса не доказывает экономию полного диалога.

### Результат 12 сентября 2026

Модель `deepseek-v4-flash`, условия и сценарий — выше. [Полные ответы, конфигурации, usage и конечные состояния](docs/context-comparison-2026-09-12.json) сохранены в репозитории. Все 71 API-вызов вернули provider usage, reasoning=0; ошибок и усечённых ответов не было. Линейная часть — 60 вызовов, дополнительная проверка веток — 11.

| --- | ---: | ---: | ---: |
| API-вызовы | 15 | 30 | 15 |

| Генерация всех вызовов | 827 | 3020 | 793 |
| **Всего токенов** | **5917** | **22337** | **8837** |

Ручная проверка считает отдельно название, идентификатор, город, цель, бюджет, срок, координатора, код макета, локальное хранение, запрет платных облаков, email-отчёт, критерий готовности, кабинет и набор данных. На ходу 15 проверяется отмена email-отчёта вместо действующего требования и добавляется приёмщик.

Sliding на ходу 11 сохранил критерий готовности и два параметра теста; на ходу 15 — также приёмщика и отмену отчёта. Ранние сведения объявлены неизвестными. При этом модель ошибочно включила объяснения «очередь — FIFO» и «стек — LIFO» в согласованные требования, а предложенные имена файлов — в ТЗ. Код макета встречался внутри этих имён, но как отдельный факт модель его не восстановила.

Facts и Branching на обоих контрольных ходах воспроизвели все проверяемые сведения. Бюджет остался 96000, отменённый отчёт не вернулся в действующие требования. В словаре Facts отмена в конце сохранена отдельным ключом `cancelled_requirement`; активное требование отчёта удалено. Итоговое ТЗ в обоих режимах содержит ответственных, ограничения и условия приёмки без обнаруженных противоречий по списку проверки.

| Удобство по наблюдаемому поведению | Вывод |
| --- | --- |
| Sliding | Не требует команд управления памятью, но потерянные условия приходится сообщать снова; итог нужно проверять на ложные требования |
| Facts | Автоматически удержал требования при ограниченном хвосте; каждый ход требует второго API-вызова, ошибки извлечения могут прервать ход |
| Branching | Позволяет вернуться к альтернативе без повторного ввода общего начала; пользователь управляет checkpoint и активной веткой командами |

Удобство оценено по этому сценарию, без пользовательского исследования; задержки не измерялись. Sliding потратил на 33,04% меньше токенов, чем полная история, ценой потери данных. У Facts финальный вход на ходу 15 меньше полного контекста на 31,60%, но общий расход **в 2,53 раза больше** из-за обновления памяти после каждого вопроса. Экономии полного диалога в этом прогоне Facts не дал.

Дополнительная проверка веток стоила **6573 токена**, отдельно от линейных 8837. В A модель сохранила 1 ноября и 3 участников, в B — 15 ноября и 8 участников. После `/switch a` ответ снова содержал 1 ноября, 3 участников, бюджет 96000, Ирину Белову и действующий email-отчёт. Срок и участники B не появились в A; отмена отчёта из продолжения `main` не проникла в ветки от раннего checkpoint. Команды копирования и переключения не делали API-вызовов.

Это один прогон конкретного сценария, не оценка общей точности моделей или гарантированная стоимость стратегий. Ответы независимых запусков различались уже на первых ходах, поэтому длина генерации тоже влияет на расход. Денежная стоимость и кеширование провайдера не сравнивались.

### Предыдущий эксперимент с summary

11 сентября 2026 на `deepseek-v4-flash` прежняя версия агента сравнивала 20 ходов без сжатия и с двумя summary: 19167 против 13630 токенов, экономия 28,89%; оба режима сохранили проверяемые факты. Это отдельный исторический эксперимент с другим сценарием. Три новые стратегии работают без summary; сравнивать эти числа с новым прогоном напрямую нельзя.

## Контракт и разработка

`Agent.respond(input)` возвращает текст (в задаче — `answer`), finishReason, результат проверки формата, оценки и usage. Сырой SDK-ответ и стек не выдаются. `getContextStatus()` возвращает режим и активную ветку; `createCheckpoint()`, `createBranch(name)`, `switchBranch(name)`, `listBranches()` управляют ветками через `AgentPort`. `getMemory()` возвращает независимую копию слоёв `short`, `working` и `long`; `setMemory(layer, key, value)`, `deleteMemory(layer, key)` (false, если записи нет) и `clearMemory(layer)` изменяют память. Необязательный `profileProvider` в `AgentOptions` — синхронный источник профиля; без него агент работает как прежде. `getTask()` возвращает копию состояния задачи с вычисленным статусом или null; `startTask(description)`, `approveTask()`, `pauseTask()`, `resumeTask()`, `clearTask()` (три последних — false без записи) управляют задачей. Без `taskRepository` задача живёт только в экземпляре агента.

`AgentSession` владеет каталогом профилей и единственным агентом и реализует `SessionPort` для CLI: `getActiveProfileId()`, `listProfileIds()` (новый отсортированный массив идентификаторов), `loadProfile(profileId)` (копия или null, без записи и переключения), `saveProfile(profileId, profile)`, `initProfile(profileId, profile)` (сохранить и выбрать одной записью), `switchProfile(profileId)`, `setProfileField`, `deleteProfileField`, `clearProfile`; остальные методы делегируются агенту. `jsonAgentRepositories(root, contextStrategy)` даёт репозитории истории, памяти и задачи в рабочем каталоге.

`AgentConfig` содержит модель и system, prompting-стратегию `direct`/`steps`/`meta`/`experts`, формат `text`/`json`/`markdown`/`yaml`, ограничения слов и токенов, stop-маркер, температуру, thinking, `contextStrategy` (null без стратегии) и N. Без `HistoryRepository` история живёт только в экземпляре агента; так же без `workingMemoryRepository` и `longTermMemoryRepository` живут соответствующие словари. Репозитории предоставляют синхронные `load()` (`HistoryState | null` или `MemoryEntries | null`) и `save(...)`; null означает отсутствие файла.

Параллельные ходы одного агента запрещены. `busy` также блокирует сброс, изменения веток, памяти и задачи во время запроса; просмотр памяти и задачи разрешён. Ошибка API, пустой ответ, незавершённый meta или ошибка facts не фиксируют ход. Непустой финальный ответ обычного чата с `validation.ok === false` сохраняется; ответ задачи с любым нарушением протокола не сохраняется.

```bash
npm run lint
npm run typecheck
npm test
npm run test:coverage
npm run build
npm start
```

Тесты не вызывают внешний API и не используют локальную историю. Fake-клиент проверяет состав запросов и управление состоянием; e2e запускает отдельные процессы с SDK и подменённым fetch во временных директориях. Эти проверки не измеряют качество реальной модели. CI выполняет линтер, типы, тесты с порогами покрытия и сборку; `npm install` подключает `.githooks/pre-commit`.
