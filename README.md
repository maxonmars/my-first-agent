# my-first-agent

Stateful CLI-агент для DeepSeek через OpenAI-совместимый API. Агент хранит диалог, рабочую и долговременную память отдельно для каждого пользователя, учитывает профиль пользователя, формирует запросы, проверяет ответы и считает токены; CLI отвечает за ввод и отображение результата.

## Подготовка и запуск

Нужен Node.js 24+.

```bash
npm install
cp .env.example .env
```

Добавьте `DEEPSEEK_API_KEY` в `.env`. Необязательный `DEEPSEEK_MODEL` по умолчанию равен `deepseek-v4-flash`. Файлы окружения, локальной истории, памяти и профилей исключены из Git.

```bash
npm run dev -- "Почему небо синее?"
npm run dev
```

Один запрос и интерактивный диалог используют историю выбранного режима и словари памяти выбранного пользователя. CLI показывает пользователя и режим при запуске, после ответа — оценку контекста, provider usage финального вызова и обновления facts, расход хода и сессии.

В интерактивном режиме `/exit` завершает диалог, `/reset` очищает диалог выбранного пользователя и режима и статистику, сохраняя рабочую и долговременную память и профиль. В Branching сброс удаляет все его ветки и checkpoint, оставляя пустую `main`. Команды доступны только в интерактивном режиме: однократный аргумент, начинающийся с `/`, завершает запуск с кодом 1 без вызова модели.

## Профили пользователей

Профиль задаёт, как агент общается с конкретным пользователем. Предпочтения не нужно повторять в каждом запросе: профиль автоматически добавляется к каждому ходу.

| Группа | Содержимое |
| --- | --- |
| `style` | Обращение, тон, подробность, язык объяснения, оформление: списки, таблицы, примеры |
| `constraints` | Правила ответа: эмодзи, код без просьбы, ограничения инструментов, уточнения и предположения |
| `context` | Устойчивые сведения: занятие, опыт, инструменты, типичные задачи, долгосрочные цели |

Условия текущей задачи по-прежнему хранятся в рабочей памяти.

### Создание и выбор

```text
/profile-init
```

CLI спрашивает идентификатор пользователя (`userId`, например `Макс` или `Владимир`), затем по одному вопросу на группу с подсказкой и прежним значением. Опрос не вызывает модель, не попадает в историю и не расходует токены.

- Существующий профиль берётся как черновик; пустой ответ сохраняет прежнее значение, для нового профиля — пропускает группу.
- Неверный идентификатор повторяет вопрос. `/cancel` отменяет опрос, `/exit` и конец ввода завершают CLI без сохранения; другие команды во время опроса не выполняются.
- После третьей группы профиль сохраняется, пользователь выбирается одной записью каталога. Если запись или загрузка данных пользователя не удались, остаётся прежний пользователь.

`userId` — локальный ключ выбора, не учётная запись: 1–64 символа, буквы, цифры, дефис или подчёркивание, первый символ — буква или цифра. Крайние пробелы обрезаются, регистр важен: `Макс` и `макс` — разные пользователи.

| Команда | Действие |
| --- | --- |
| `/profile` | Показать активного пользователя и профиль |
| `/profile load userId` | Выбрать существующего пользователя |
| `/profile set style\|constraints\|context значение` | Заменить группу; значение — остаток строки |
| `/profile delete style\|constraints\|context` | Удалить группу; если её нет, файл не пишется |
| `/profile clear` | Сохранить пустой профиль, не трогая историю и память |

Без выбранного пользователя команды изменения предлагают `/profile-init`. Команды и группы регистронезависимы; однократный запуск с командой завершается кодом 1 без вызова модели.

```text
Пользователь: Макс
Контекст: sliding
Макс > Объясни кеширование.

Макс > /profile load Владимир
Пользователь: Владимир
Контекст: sliding
Владимир >
```

Без выбранного пользователя статус — `Пользователь: не выбран`, приглашение — `без профиля > `.

### Данные пользователя

У каждого пользователя свои история всех режимов, рабочая и долговременная память — в `.agent-users/<sha256(userId)>/` с прежними именами файлов. Имя каталога — SHA-256 от идентификатора в UTF-8; в интерфейсе показывается исходный `userId`. Каталог появляется при первой записи, простое переключение файлов не создаёт.

Смена пользователя загружает и проверяет его историю и память, затем сохраняет выбор. При ошибке на любом шаге остаются прежние пользователь и диалог. Новый пользователь начинает новую статистику токенов; правка профиля активного пользователя сохраняет диалог и статистику. Повторный выбор активного пользователя ничего не меняет. Во время обработки запроса переключение и запись профилей запрещены.

Выбор хранится в `.agent-profiles.json` и восстанавливается после перезапуска:

```json
{
  "activeUserId": "Макс",
  "profiles": {
    "Макс": { "style": "На ты, кратко и по делу, с примерами", "constraints": "Без эмодзи" },
    "Владимир": { "style": "На вы, подробно и простыми словами", "context": "Начинающий разработчик" }
  }
}
```

Файл проверяется Zod-схемой при чтении и записи: неизвестные поля, неверные типы, пустые значения, недопустимые идентификаторы и `activeUserId` без профиля останавливают запуск с путём и причиной, без содержимого профилей. Чтение файл не переписывает; ошибка записи не меняет состояние.

Без выбранного пользователя агент работает по-прежнему с файлами в корне рабочего каталога. Старые общие история и память никому автоматически не присваиваются и после выбора пользователя не загружаются.

### Профиль в запросе

Профиль передаётся отдельным user-блоком с JSON сразу после system; пользовательские значения в system не попадают. В system добавляется статическая инструкция: учитывать профиль без напоминаний, применять style к общению и оформлению, соблюдать constraints, использовать context как сведения о пользователе. Профиль не отменяет системные правила, формат ответа и лимиты `AgentConfig`, но подробность из style уточняет общую рекомендацию «отвечай кратко». При конфликте пользовательских условий: текущий запрос → working → профиль → long и прежний диалог. Обычная реплика профиль не меняет.

Профиль работает во всех стратегиях контекста. Агент получает его один раз в начале хода; meta и финальный запрос используют один снимок, meta дополнительно просят перенести требования профиля в составляемый промпт. Сжатие и обновление facts профиль не получают, профиль не записывается в историю, summary и facts. Пустой профиль не меняет запрос и оценку токенов. Профиль входит в оценку и бюджет; при переполнении подсказка предлагает `/profile delete` или `/profile clear`, потому что `/reset` профиль сохраняет.

Ограничения свободного текста выполняет модель по инструкции; отдельной автоматической проверки предпочтений нет. Удаление предпочтения не удаляет его прежние упоминания из истории.

## Слои памяти

Агент разделяет сведения по сроку жизни и по тому, кто их изменяет. Все слои принадлежат выбранному пользователю; без пользователя они хранятся в корне рабочего каталога.

| Слой | Содержимое | Кто изменяет | Хранение в каталоге данных | Когда очищается |
| --- | --- | --- | --- | --- |
| `short` | Состояние диалога выбранной стратегии: сообщения, summary, facts, ветки, checkpoint | Обработка ходов, `/reset`, команды веток | Файл истории режима | `/reset` или `/memory clear short` |
| `working` | Цель, ограничения, параметры и решения текущей задачи | Только команды `/memory` | `.agent-memory.working.json` | `/memory clear working` |
| `long` | Сведения, предпочтения, сохранённые знания и решения | Только команды `/memory` | `.agent-memory.long-term.json` | `/memory clear long` |

Все три слоя восстанавливаются после перезапуска; статистика расхода начинается с нуля.

**Стратегия контекста** определяет, как обрабатывается `short`: полная история, summary, окно, facts или ветки. **Рабочая и долговременная память** от стратегии не зависят и отдельного переключателя не имеют: непустые словари добавляются к запросу в любом режиме. Facts — автоматически извлечённая производная диалога и относятся к `short`; их обновление не пишет в `working` или `long`, прежние facts в словари не переносятся. Автоматического распределения сведений по слоям нет: сохранять в `working` и `long` нужно явной командой.

### Команды

| Команда | Действие |
| --- | --- |
| `/memory` | Показать все три слоя |
| `/memory show short\|working\|long` | Показать один слой; `short` — со всеми производными данными и ветками |
| `/memory set working\|long ключ значение` | Создать или заменить запись |
| `/memory delete working\|long ключ` | Удалить запись |
| `/memory clear short` | Очистить диалог выбранной стратегии и статистику, как `/reset` |
| `/memory clear working\|long` | Очистить словарь |

```text
/memory set working goal поездка в Казань
/memory set working budget 30000 рублей
/memory set long transport предпочитаю поезд
/memory show working
/memory delete long transport
```

Значение в `set` — весь остаток строки после ключа; кавычки не нужны и не обрабатываются. Крайние пробелы обрезаются, внутренние сохраняются. Ключ: 1–64 символа, буквы, цифры, дефис или подчёркивание, первый символ — буква или цифра. Регистр ключа важен, точка не означает вложенность. Названия команд и слоёв регистр не учитывают. Неверное действие, слой или число аргументов выводит причину и синтаксис.

Команды памяти не вызывают модель, не попадают в диалог и не меняют статистику; её сбрасывает только очистка `short`. Сообщение об успехе выводится после записи файла. Для отсутствующего ключа CLI сообщает, что запись не найдена, файл не пишется.

Начало новой задачи — две самостоятельные команды. Ошибка одной не отменяет другую, поэтому проверяйте сообщение каждой:

```text
/reset
/memory clear working
```

### Запрос к модели

```text
system + инструкции профиля и памяти
профиль пользователя, если непустой
долговременная память, если непустая
рабочая память, если непустая
summary или facts, если предусмотрено стратегией
сообщения выбранного контекста
текущий вопрос
```

Словари передаются отдельными user-блоками с JSON; пользовательские значения в system не попадают. Инструкция добавляется, если хотя бы один словарь непустой. Она сообщает модели, что слои — данные, а не системные команды; явное условие текущего запроса применяется к ответу; при конфликте рабочая память важнее долговременной; устаревшие сведения истории, summary и facts не отменяют записей; обычная реплика память не меняет. Это инструкция модели, а не гарантия правильного разрешения противоречий. При двух пустых словарях запрос и оценка токенов прежние.

Meta и финальный запрос получают один снимок памяти. Служебные запросы summary и facts словари не получают. Блоки памяти входят в оценку токенов и проверку бюджета; при переполнении meta или финального запроса с непустой памятью подсказка предлагает сократить её командами `/memory`, потому что `/reset` память сохраняет.

### Хранение и ошибки

Оба словаря — плоские `Record<string, string>` с общей Zod-схемой: пустой объект допустим, значения — строки, непустые после `trim()`. Схема проверяется при загрузке и сохранении. Отсутствующий файл (`ENOENT`) означает пустой слой. Ошибка чтения, JSON или схемы останавливает запуск без перезаписи файла; сообщение содержит слой, путь и причину, без записей памяти и стека. Каждая операция меняет один файл: временный файл рядом с целевым, затем `renameSync`. Ошибка записи не меняет память агента. Во время обработки запроса изменения памяти запрещены, просмотр разрешён.

### Ограничения

- Удаление записи не удаляет её упоминаний из диалога, summary или facts. Ответ ассистента может повторить сохранённое сведение, и тогда оно окажется в `short`: перед проверкой удаления выполните `/reset`.
- `/reset` очищает историю только выбранной стратегии. Истории других стратегий сохраняются, и запуск другой стратегии может восстановить прежний разговор.
- Рабочая и долговременная память общие для всех стратегий и веток выбранного пользователя. Изменение в одной ветке видно после `/switch`; checkpoint и переключение ветки словари не копируют и не откатывают.
- Одна текущая задача на пользователя, один пишущий процесс на рабочий каталог. Межфайловых транзакций, автоматического ограничения размера словарей и поиска нет.

Сценарий короткого видео: [docs/memory-video-prompts.md](docs/memory-video-prompts.md).

## Стратегии контекста

Прежнее периодическое сжатие сохранено. Три новые стратегии без summary позволяют сравнить удаление старого контекста, отдельную память фактов и независимые продолжения диалога.

Выбор действует при запуске, через окружение или `.env`:

```bash
AGENT_CONTEXT_STRATEGY= npm run dev
AGENT_CONTEXT_STRATEGY=compression npm run dev
AGENT_CONTEXT_STRATEGY=sliding npm run dev
AGENT_CONTEXT_STRATEGY=facts npm run dev
AGENT_CONTEXT_STRATEGY=branching npm run dev
```

Пустое значение, пробелы или отсутствие `AGENT_CONTEXT_STRATEGY` означают полную историю без обработки контекста (`contextStrategy: null`). Неизвестное непустое значение — ошибка. Обычный режим и `compression` продолжают один диалог в `.agent-history.json`; у `sliding`, `facts`, `branching` свои истории. `AGENT_HISTORY_COMPRESSION` больше не читается: оставшуюся переменную в старом `.env` можно удалить.

| Режим | Что сохраняется | Стек для ответа |
| --- | --- | --- |
| Без стратегии (пусто) | Вся доступная история и прежнее summary, если есть | System + прежнее summary + вся история + новый вопрос |
| Compression | Summary + несжатый хвост | System + summary как данные + хвост + новый вопрос |
| Sliding Window | Последние N сообщений | System + N сообщений + новый вопрос |
| Facts | Словарь ключ-значение + последние N сообщений | System + facts как данные + N сообщений + новый вопрос |
| Branching | Полные истории веток, checkpoint, активная ветка | System + история активной ветки + новый вопрос |

`AGENT_KEEP_LAST_MESSAGES=10` задаёт N: положительное чётное безопасное целое, **число сообщений, не ходов**. Один завершённый ход — два сообщения. Окно может быть короче N в начале диалога. N проверяется для всех конфигураций; в Compression задаёт сохраняемый хвост при сжатии, в Branching не ограничивает историю.

### Без стратегии — полная история

```dotenv
AGENT_CONTEXT_STRATEGY=
```

Сообщения сохраняются и отправляются целиком: без обрезания, извлечения facts, ветвления и новых summary. Контекст растёт до локального бюджета или лимита API. На чистой истории это system + весь диалог + новый вопрос. N в этом режиме не ограничивает историю.

Если диалог уже сжимался, прежнее summary остаётся частью контекста. Отключение стратегии не возвращает вытесненные сообщения и не удаляет сохранённые сведения. Для чистого диалога используйте `/reset`. Выбор `compression` возобновляет периодическое сжатие той же истории.

### Compression — прежний режим

```dotenv
AGENT_CONTEXT_STRATEGY=compression
```

Выбор `compression` включает сжатие без дополнительного флага. При `messages.length >= N + 10` перед новым вопросом весь префикс кроме последних N сообщений заменяется summary. Порция накопления — 10 сообщений. При N=10 сжатие происходит перед вопросами 11, 16, 21; после ответа сохраняются summary и N+2 сообщения, между сжатиями хвост растёт.

Служебный запрос получает только предыдущее summary и вытесняемый префикс. Используются та же модель, `max_tokens=512`, thinking disabled, без meta и политики финального ответа. Пустое или усечённое summary отклоняется после учёта usage. Meta и финальный запрос получают один кандидат summary и хвоста; сохранение происходит вместе с новой парой.

Чтобы отключить сжатие, оставьте `AGENT_CONTEXT_STRATEGY` пустым. В `sliding`, `facts` и `branching` суммаризация не выполняется.

### Sliding Window

Перед запросом выбираются последние N завершённых сообщений. После успешного ответа новая пара добавляется, сохраняются только последние N сообщений, включая эту пару. Старый префикс удаляется и из памяти, и из файла. Новый вопрос в API идёт сверх N; system не считается сообщением окна.

Если N уменьшили после перезапуска, более длинная история ограничивается при подготовке запроса и обрезается на диске после следующего успешного ответа. Полного архива нет.

### Sticky Facts / Key-Value Memory

После каждого нового сообщения пользователя модель обновляет весь JSON-словарь `Record<string, string>`. Например:

```json
{"project":"Север","budget":"96000 рублей","storage":"только локально"}
```

Служебный запрос получает прежний словарь, последние N сообщений и вопрос. Инструкция требует стабильных ключей, точных значений, замены исправленных фактов и удаления явно отменённых. Предложение ассистента становится договорённостью только после согласия пользователя. Zod проверяет словарь непустых строк; правильность извлечения зависит от модели.

Обновлённые facts допускают в ключах только латинские буквы, цифры, `_` и `-`, первый символ — латинская буква. Инструкция просит английские названия в snake_case, например `conversation_code`; язык значений сохраняется. Старые ключи на других языках загружаются без изменения файла и передаются модели для переименования при следующем обновлении. Ответ модели с недопустимым ключом отклоняется без сохранения хода.

JSON mode задаёт JSON-формат, но не проверяет схему словаря. Например, `{"budget":84000}` — корректный JSON, но facts требует `{"budget":"84000 рублей"}`. Инструкция содержит пример плоского словаря и требует записывать числа, даты и логические факты строками. При нарушении схемы ошибка показывает причину и полученный тип, без содержимого фактов; уточнение инструкции не гарантирует соблюдение схемы моделью.

Обновлённые facts используются уже в ответе на текущий вопрос. Они передаются отдельным user-блоком с пометкой «данные», не добавляются в system. Meta и финальный запрос получают один кандидат контекста. Facts и новая пара сохраняются вместе только после непустого финального ответа и успешной записи.

Извлечение использует ту же модель, JSON mode, `max_tokens=512`, thinking disabled, без настроек формата и ограничений финального ответа. При пустом ответе, усечении, некорректном JSON или неверной структуре ход завершается ошибкой; память не меняется, usage ответа учитывается. Автоматического повтора или восстановления нет. Словарь не имеет политики удаления по размеру: слишком большой результат или вход может привести к ошибке лимита.

### Branching

Начальная ветка — `main`. Доступны один checkpoint и именованные ветки:

```text
Общая цель проекта — локальный учёт заявок.
/checkpoint
/branch вариант-а
В этом варианте срок — 1 ноября.
/branch вариант-б
В этом варианте срок — 15 ноября.
/switch вариант-а
Какой срок выбран в этом варианте?
/branches
```

`/checkpoint` сохраняет копию активного диалога; повторная команда заменяет снимок. `/branch имя` создаёт ветку **из checkpoint**, даже если текущая ветка уже продолжена, и делает новую активной. `/switch имя` выбирает существующую ветку. `/branches` показывает число сообщений и помечает активную ветку `*`.

Имена уникальны, 1–64 символа: буквы, цифры, дефис, подчёркивание; первый символ — буква или цифра. Повторное имя не перезаписывает ветку. Без checkpoint создать ветку нельзя. Команды доступны в интерактивном Branching, не обращаются к LLM и не расходуют токены.

В запрос входит полный диалог только активной ветки. Другие ветки и checkpoint в API не отправляются. История растёт до локального бюджета или предела провайдера. Объединения веток и дерева checkpoint нет.

## Сохранение между запусками

Каждый режим использует свой файл истории в каталоге данных: `.agent-users/<sha256(userId)>/` выбранного пользователя или `process.cwd()` без него. Каталог профилей — всегда `process.cwd()/.agent-profiles.json`.

| Режим | Файл | Пустое состояние |
| --- | --- | --- |
| Без стратегии / Compression | `.agent-history.json` | `{"summary":null,"messages":[]}` |
| Sliding | `.agent-history.sliding.json` | `{"kind":"sliding","messages":[]}` |
| Facts | `.agent-history.facts.json` | `{"kind":"facts","messages":[],"facts":{}}` |
| Branching | `.agent-history.branching.json` | `{"kind":"branching","activeBranch":"main","branches":{"main":[]},"checkpoint":null}` |

Рабочая и долговременная память хранятся отдельно, в `.agent-memory.working.json` и `.agent-memory.long-term.json` того же каталога, и общие для всех режимов пользователя; пустой словарь сохраняется как `{}`.

Обычный режим и Compression используют прежний `.agent-history.json` и сохраняют прежний формат `{ summary, messages }`. Старый JSON-массив читается как сообщения с summary=null без перезаписи при загрузке; следующий успешный save пишет объект. Три новых режима используют свои файлы и не читают старую историю. Если формат загруженного состояния не соответствует выбранному режиму, запуск останавливается.

Репозиторий проверяет структуру при чтении и записи, завершённость и порядок пар во всех ветках и checkpoint, наличие `main` и активной ветки. `kind` обозначает формат данных. Конфигурация, API-ключ, system, внутренние запросы и usage не сохраняются. После перезапуска восстанавливаются данные и активная ветка, расход сессии начинается с нуля.

Изменения выполняются как кандидат → запись временного файла рядом с основным → `renameSync` → обновление состояния агента. Это относится также к checkpoint, созданию и переключению ветки, сбросу и командам памяти. При ошибке записи прежнее состояние остаётся, потраченные токены учитываются. `/reset` сохраняет пустое состояние, не удаляя файл, и не затрагивает другие режимы.

Только `ENOENT` означает отсутствие истории или словаря памяти. Повреждённый JSON или ошибка чтения останавливают запуск с причиной и путём, без содержимого диалога или памяти и без стека. Автоматического исправления файла нет. Один файл рассчитан на один пишущий процесс; атомарная замена не решает конфликт одновременных CLI.

## Токены и бюджет

`tokenEstimate.questionTokens` оценивает вопрос после `trim()`. `contextTokens` — весь стек финального запроса до генерации, включая блоки памяти. Оценка `Math.ceil(content.length / 4)` — эвристика по длине JavaScript-строк, без служебных надбавок; это не токенизатор DeepSeek. CLI отмечает оценки знаком `≈`.

`usage.summaryCall` — расход сжатия или `null`, если его не было. `usage.factsCall` — расход обновления словаря или `null` в других режимах. `finalCall` — только финальный запрос, `turn` — сумма summary + facts + meta + финального запроса, `session` — все полученные API-ответы текущего экземпляра агента. Reasoning уже входит в completion и повторно не прибавляется. При отсутствующем usage агент возвращает нулевой fallback, а не измеренный нулевой расход.

```dotenv
AGENT_MAX_INPUT_TOKENS=2000
```

Пустое или отсутствующее значение отключает бюджет. Иначе нужен положительный безопасный integer. Перед каждым API-вызовом, включая summary, извлечение facts и подготовку meta, оценивается подготовленный стек. Равенство лимиту разрешено; превышение не вызывает API, не меняет контекст и освобождает busy. Уже потраченный usage предыдущих вызовов остаётся.

Это учебный лимит входа: он не резервирует генерацию и не гарантирует принятия запроса провайдером. `maxTokens` ограничивает генерацию через `max_tokens`. Непустой усечённый **финальный** ответ сохраняется с предупреждением; усечённый ответ summary или извлечения facts отклоняется.

## Сравнение с реальной моделью

Сценарий выполнял 15 одинаковых пользовательских ходов на каждой стратегии. Branching проходит линейную часть в `main`. На пятом ходу сохраняется checkpoint для отдельной проверки веток.

| Ходы | Содержание |
| --- | --- |
| 1–4 | «Север», SN-047, Томск, локальный учёт заявок; 84000 рублей; 17 октября 2026; Ирина Белова; кедр-731; локальное хранение, запрет платных облаков, еженедельный email-отчёт |
| 5 | Бюджет исправлен на 96000 |
| 6–10 | Промежуточные вопросы; критерий — 12 обработанных заявок; кабинет 314 и trial-B9 |
| 11 | Контроль основных фактов и согласованных требований |
| 12 | Email-отчёт отменён |
| 13–14 | Приёмку проводит Павел Орлов; промежуточный вопрос |
| 15 | Итоговое ТЗ с действующими и отменёнными требованиями |

Перед прогоном фиксируется список проверки: на ходу 11 нужны все **14 фактов** из ходов 1–5, 7 и 10 с актуальным бюджетом; на ходу 15 те же факты с отменённым email-отчётом и добавленным приёмщиком (**15 пунктов**). Считаем явное воспроизведение, пропуски, противоречия и выдуманные значения. «Неизвестно» честнее выдуманного значения, но не считается сохранением факта.

Дополнительная проверка Branching: две ветки от checkpoint пятого хода, по пять реплик в каждой. В A срок 1 ноября, 3 участника; в B срок 15 ноября, 8 участников. После переключения в A запрашиваются её условия. Общий бюджет — 96000, координатор — Ирина Белова; email-отчёт в обеих ветках ещё действует, потому что отмена из `main` произошла после checkpoint. Чужие сроки и число участников не должны попадать в ответ. Токены этого эксперимента считаются отдельно.

### Условия

Реальные API-вызовы на вымышленных данных с отдельными чистыми историями. Условия: direct/text, температура 0, thinking disabled, одинаковый system, N=10, бюджет входа и лимиты финального ответа отключены. Facts дополнительно выполняет 15 служебных запросов. Детерминированность ответов при температуре 0 не гарантируется.

Расход суммировался по `usage.turn.totalTokens` отдельно для линейной части и дополнительных веток; сессионные снимки складывать нельзя, в Branching они включают оба эксперимента. Стоимость facts входит в итог. При отсутствии provider usage измерение неполное. Уменьшение одного входного запроса не доказывает экономию полного диалога.

Facts и Branching на обоих контрольных ходах воспроизвели все проверяемые сведения. Бюджет остался 96000, отменённый отчёт не вернулся в действующие требования. Итоговое ТЗ в обоих режимах содержит ответственных, ограничения и условия приёмки без обнаруженных противоречий по списку проверки.

Удобство оценено по этому сценарию, без пользовательского исследования; задержки не измерялись. Sliding потратил на 33,04% меньше токенов, чем полная история, ценой потери данных. Дополнительная проверка веток стоила **6573 токена**, отдельно от линейных 8837. В A модель сохранила 1 ноября и 3 участников, в B — 15 ноября и 8 участников. Это один прогон конкретного сценария, не оценка общей точности моделей или гарантированная стоимость стратегий. Ответы независимых запусков различались уже на первых ходах, поэтому длина генерации тоже влияет на расход. Денежная стоимость и кеширование провайдера не сравнивались.

## Контракт и разработка

`Agent.respond(input)` возвращает текст, finishReason, результат проверки формата, оценки и usage. Сырой SDK-ответ и стек не выдаются. `getContextStatus()` возвращает режим и активную ветку; `createCheckpoint()`, `createBranch(name)`, `switchBranch(name)`, `listBranches()` управляют ветками через `AgentPort`. `getMemory()` возвращает независимую копию слоёв `short`, `working` и `long`; `setMemory(layer, key, value)`, `deleteMemory(layer, key)` (false, если записи нет) и `clearMemory(layer)` изменяют память. Необязательный `profileProvider` в `AgentOptions` — синхронный источник профиля; без него агент работает как прежде.

`AgentSession` владеет каталогом профилей и агентом выбранного пользователя и реализует `SessionPort` для CLI: `getActiveUserId()`, `loadProfile(userId)` (копия или null, без записи), `saveProfile(userId, profile)`, `initProfile(userId, profile)` (сохранить и выбрать одной записью), `switchUser(userId)`, `setProfileField`, `deleteProfileField`, `clearProfile`; остальные методы делегируются агенту.

`AgentConfig` содержит модель и system, prompting-стратегию `direct`/`steps`/`meta`/`experts`, формат `text`/`json`/`markdown`/`yaml`, ограничения слов и токенов, stop-маркер, температуру, thinking, `contextStrategy` (null без стратегии) и N. Без `HistoryRepository` история живёт только в экземпляре агента; так же без `workingMemoryRepository` и `longTermMemoryRepository` живут соответствующие словари. Репозитории предоставляют синхронные `load()` (`HistoryState | null` или `MemoryEntries | null`) и `save(...)`; null означает отсутствие файла.

Параллельные ходы одного агента запрещены. `busy` также блокирует сброс, изменения веток и памяти во время запроса; просмотр памяти разрешён. Ошибка API, пустой ответ, незавершённый meta или ошибка facts не фиксируют ход. Непустой финальный ответ с `validation.ok === false` сохраняется.

```bash
npm run lint
npm run typecheck
npm test
npm run test:coverage
npm run build
npm start
```

Тесты не вызывают внешний API и не используют пользовательскую историю. Fake-клиент проверяет состав запросов и управление состоянием; e2e запускает отдельные процессы с SDK и подменённым fetch во временных директориях. Эти проверки не измеряют качество реальной модели. CI выполняет линтер, типы, тесты с порогами покрытия и сборку; `npm install` подключает `.githooks/pre-commit`.
